# A · Daylight 운영 전환 구현 계획

작성일: 2026-10-22 (Asia/Seoul)
보완일: 2026-10-22 — 현재 코드의 상태 적용·준비 저장·읽기 전용 내보내기 경로와 CI를 대조했다. 이번 보완은 문서 검토이며 앱 동작 검증 결과가 아니다.

**상태: 2026-10-23 후보 구현·검증·공개 검토본 배포 완료. 운영 전환은 미승인.** 후보는 `codex/daylight-implementation`에서 관리한다. 운영 전환은 공개 검토 결과로 별도 승인받는다. 검증 근거와 남은 항목은 [구현 기록](archive/2026-10-23-daylight-implementation.md)을 따른다.

후속 비교에서 발견한 설정 메뉴·포커스 문제의 수정과 현재 로컬 검증은 [전환 준비 검토](archive/2026-10-23-daylight-readiness.md)를 따른다. 아래 완료 체크리스트의 CI·공개 배포 표시는 당시 후보의 이력이며 후속 미배포 수정본의 CI 성공을 보증하지 않는다.

## 1. 문서의 역할과 기준

- 출발점: [2026-10-22 인계](archive/2026-10-22-daylight-handoff.md). 그 문서의 미결 사항 중 적용 계획 범위와 보조 카드 방향은 이번 대화에서 결정되었다. 과거 인계는 당시 기록으로 보존한다.
- 현재 사용·저장 정책: [사용자 안내서](USER_GUIDE_KO.md).
- 기존 구조와 데이터 흐름: [기술 설명서](PROJECT_GUIDE_KO.md).
- 실행·검증·공개 초안 배포: [운영 안내서](OPERATIONS_KO.md#ui-concepts).
- 시각 기준: [A안 원본](ui-concepts/a.html), [공개 A안](https://pca01008.github.io/us-west-2027-trip/ui-preview/a.html). 공개 주소는 배포 때 바뀌는 화면이며 고정 스냅샷이 아니다.

이 문서는 변경 계획만 관리한다. 현재 운영 앱의 사용법을 미래 동작으로 미리 덮어쓰지 않는다. 구현이 끝나면 실제 동작은 각 기준 안내서에 반영하고 이 문서에는 단계별 완료 여부와 검증 근거를 연결한다.

## 2. 확정한 범위

### 사용자와 확정한 사항

1. A안 초안 개선뿐 아니라 **운영 앱 전환까지 계획**한다. 실제 적용은 별도 승인한다.
2. 일정의 숙소 카드는 **선택 날짜와 연결**한다.
3. 준비 화면은 기존 목록의 항목을 직접 중요 표시하여 보여준다. 자동 추천·자동 우선순위 선정은 하지 않는다.
4. **중요하면서 미완료인 항목만 강조 영역에 표시**한다. 완료하면 제외한다.
5. 기존 기능과 목적을 유지한다. 불가피한 기능·저장 정책 변경은 먼저 설명하고 확인한다.
6. 여행 전 PC 계획·예산 편집과 여행 중 모바일 조회를 같은 비중으로 고려한다.
7. 세이지·흰 바탕·녹색 강조를 유지한다. B/C는 비교 기록으로 남긴다.
8. 사용자는 원격에서 검토하므로 결과는 공개 HTTPS 주소로 제공한다.

### 이 계획의 구현 기본안

아래는 위 요구사항을 구체화한 기본안이며 별도의 사용자 확정 사실로 취급하지 않는다. 구현 중 모순이 발견되면 대안을 먼저 정리한다.

- 숙소 카드는 그날 밤 머무는 곳을 표시한다. 체크인 날짜는 포함하고 체크아웃 날짜는 제외한다.
- 체크아웃 내역은 당일 일정에 남긴다. 같은 날 숙소를 옮기면 카드에는 새 숙소를 표시한다.
- 준비 화면의 고정 LA 숙소 카드는 제거한다. 숙소 안내는 일정 화면으로 모은다.
- 중요 항목이 없거나 모두 완료되면 강조 영역을 숨긴다. 완료를 해제하면 다시 표시한다.
- 중요 항목의 순서는 현재 준비 목록 순서를 따른다. 별도 순위·마감일·추천 점수는 추가하지 않는다.
- 기존 HTML·JavaScript·Supabase와 테스트 도구를 활용한다. 새 프레임워크, 상태 관리 라이브러리, 별도 서버, DB 테이블은 기본 범위에 넣지 않는다.

## 3. 현재 구현에서 확인한 출발점

| 영역 | 현재 상태 | 구현 시 의미 |
|---|---|---|
| 운영 앱 | `index.html`에 화면·편집·인증·저장 로직이 함께 있음 | A안 초안 파일로 교체하지 않고 기존 기능에 화면을 적용 |
| 저장 형식 | schemaVersion 5, 일정·준비 목록은 `html`, 가계부는 배열, 체크는 별도 배열 | DOM 변경과 보조 영역 추가가 저장 결과에 미치는 영향을 먼저 확인 |
| 상태 수집·적용 | `captureState()`는 main을 복제하고 `applyState()`는 main을 저장 HTML로 교체 | 보조 영역의 중복 저장과 복원 후 레이아웃 유실 방지 |
| 준비 항목 | 안정적인 `data-check-id` 사용 | 중요 표시는 배열 위치가 아닌 항목 ID에 귀속 |
| 준비 저장 | `checklistItems()`·`patchChecklist()`가 항목을 읽고 다시 생성 | 중요 속성을 모든 경로에 전달하지 않으면 체크만 해도 유실될 수 있음 |
| 목록 충돌 비교 | `checklistShape()`는 현재 ID·문구를 비교 | 중요 표시만 바뀌어도 변경·충돌을 감지하도록 확장 필요 |
| 숙소 | 기본 일정에 체크인·체크아웃·사진·지도는 있으나 명시적인 숙박 기간 필드는 없음 | 제목으로 기간을 추측하지 않고 명시적인 연결 정보를 추가 |
| A안 데이터 | 기본 설정에서 만든 표시용 스냅샷, 시각·도시·체크·지출 일부 고정 | 운영에서는 현재 공유본·초안·시간을 기준으로 렌더링 |
| A안 설정 | 배치 검토용 비활성 버튼 | 실제 권한·편집·저장 상태에 맞춰 연결 |

`docs/ui-concepts/data.js`, `timetable-core.js`, `ui-preview/`는 생성물이다. 변경이 필요하면 생성기·원본을 수정하고 다시 생성한다.

## 4. 화면과 사용자 동작

### 4.1 공통 화면·탐색

- PC는 왼쪽 주 메뉴, 모바일은 하단 주 메뉴로 일정·준비·가계부를 전환한다.
- 설정은 편집과 저장 / 파일 / 화면 그룹을 유지한다. 기능별 인증·활성 상태를 기존 로직과 연결한다.
- 저장 상태, 실패, 초안 복구, 버전 미리보기 같은 중요한 안내는 설정 메뉴를 열어야만 보이는 곳에 숨기지 않는다.
- 여행 전 준비 → 여행 중 현지 날짜 일정 → 여행 후 가계부라는 기존 첫 화면 선택 정책을 유지한다.
- 사용자가 탭·날짜를 선택한 뒤 시각 갱신이나 서버 갱신이 그 선택을 덮어쓰지 않는다.
- 준비 탭 진입·재선택은 맨 위 이동과 제목 포커스를 적용한다. 나머지 탐색은 내용·입력·포커스를 보호한다.
- 실제 시계는 기존 서울·목적지 시간대 계산을 사용한다. 고정된 여행 중 날짜와 도시는 제거한다.
- 초안의 ‘다음 일정’ 강조를 운영에 옮기기 전 현행 시간 처리와 대조한다. 정확한 미래 시작 시각만 대상으로 삼고 미정·다른 시간대·지난 날짜를 임의로 다음 일정으로 판단하지 않는다.

**탐색 구현 기준:** 주 메뉴·날짜 선택·시간표 범위는 저장 데이터와 분리한 화면 상태로 관리한다. 기존 `.day-radio`, 날짜 ID, `.tabs`, `.panel.day`에 연결된 편집·시간표·내보내기 동작을 먼저 대응시킨다. PC·모바일 메뉴가 같은 선택 상태를 사용하고, 중복 ID나 화면 밖에서 키보드로 접근되는 숨은 메뉴가 생기지 않게 한다. 새 탐색을 위해 원본 일정·체크리스트 DOM을 복제하지 않는다.

### 4.2 일정·시간표

- 일별 일정 / 시간표와 1일 / 전체의 시각적 위계를 구분한다.
- 일정의 확인 사항은 항상 보이게 유지한다. 사진·지도·참고 링크·기존 비용 정보가 초안의 단순화 과정에서 빠지지 않도록 확인한다.
- 시간 입력, 일정 분류, 추가·삭제, 사진·지도 편집, 실행 취소·다시 실행을 유지한다.
- 시간표는 기존 운영 시간 해석·겹침 배치·자정 연결·미정 및 다른 시간대 분리를 재사용한다.
- PC 전체 / 모바일 1일 기본값을 유지하고, 전체와 1일 사이에서 선택 날짜가 유지되도록 한다. 현재 초안에 흩어진 반응형 기준은 운영 기준과 일치시킨다.
- 상세 창의 키보드 진입, Esc 닫기, 닫은 뒤 원래 카드로 포커스 복원을 유지한다.

### 4.3 날짜별 숙소

**입력·저장 기본안:** 기존 숙소 일정에 ‘숙소 카드에 표시’와 체크아웃 날짜를 지정한다. 체크인 날짜는 그 일정의 날짜를 사용하고, 이름·사진·지도는 해당 일정에서 읽는다. 독립적인 숙소 목록 편집 화면과 중복 주소 입력은 만들지 않는다.

| 상황 | 표시·처리 기준 |
|---|---|
| 체크인일 ≤ 선택일 < 체크아웃일 | 해당 숙소 카드 표시 |
| 체크아웃만 있고 새 숙소가 없는 날 | 숙소 카드 숨김, 체크아웃은 일정에 유지 |
| 같은 날 이전 숙소 체크아웃·새 숙소 체크인 | 새 숙소 카드 표시 |
| 투어 숙박 등 숙소 이름·사진 부족 | 지정된 일정의 실제 제목 사용, 사진 없이도 표시 가능 |
| 지도 없음 | 지도 버튼 숨김 |
| 기간 미지정·연결 일정 삭제 | 임의 숙소를 표시하지 않음 |
| 종료 날짜가 시작 이하 또는 날짜가 유효하지 않음 | 적용 전 오류 안내, 기존 입력 유지 |
| 두 숙박 기간이 겹침 | 편집 시 충돌 안내; 가져온 데이터는 임의로 하나를 선택하지 않고 후보와 확인 필요 상태 표시 |

숙소 카드는 조회용이다. 변경은 원본 숙소 일정에서 한다. 날짜 이동만으로 저장·초안 상태가 바뀌지 않아야 한다.

숙박 기간은 목적지 기준의 **달력 날짜**로 비교한다. 조회하는 기기의 시간대나 UTC 변환으로 체크인·체크아웃 날짜가 하루씩 바뀌지 않도록 한다. 체크아웃은 마지막 여행 날짜의 다음 날까지 허용하고, 그 밖의 날짜는 현재 여행 범위에 맞게 검증한다. 형식만 맞는 `2027-02-30` 같은 값도 거부한다. 숙소 지정 여부는 관광·식사·숙소·휴식 등의 색상 분류와 별개로 취급하며 분류만으로 숙소 카드를 생성하지 않는다.

숙소 원본의 문구·사진·지도를 편집하면 카드도 현재 초안을 보여주고 실행 취소·다시 실행에 따라 돌아간다. 숙소 지정 해제는 연결 속성만 제거하며 일정·사진을 삭제하지 않는다. 숙박 기간 입력 창의 적용은 일정 초안을 바꾸는 동작이고, 공개 반영에는 기존 공유 저장이 필요하다.

현재 서버 공유본은 기본 설정과 다를 수 있다. 초기 숙소 연결을 기본 설정의 제목·배열 순서로 서버에 강제 적용하지 않는다. 기존 공유본에는 연결이 없으면 카드를 숨기고, 사용자가 숙소 일정에서 기간을 지정할 수 있도록 한다. 초기 연결을 대신 설정할 경우 실제 공유본을 기준으로 검토하고 별도 데이터 편집 범위 안에서 수행한다.

### 4.4 중요 준비 항목

- 기존 목록 편집 창에 항목별 ‘중요’ 토글을 추가한다. 색상만으로 구분하지 않고 라벨·접근 가능한 선택 상태를 제공한다.
- 새 항목은 미완료·중요 해제로 시작한다. 중요 표시 변경은 목록 편집 창의 저장으로 반영되며 취소·Esc로 닫으면 버린다.
- 보기 화면의 ‘먼저 확인해요’는 중요하면서 미완료인 항목의 문구를 표시한다. 원본 항목으로 이동해 체크할 수 있게 한다.
- 강조 영역에 두 번째 체크박스 집합을 만들지 않는다. 기존 체크 집계와 `checks` 배열에 중복 항목이 들어가지 않게 한다.
- 체크 저장 중에는 중복 조작을 막고, 성공 후 강조 영역에서 제외한다. 실패 시 항목과 체크 상태를 유지·복구하고 재시도를 제공한다.
- 문구 수정·순서 변경·체크 완료 후에도 중요 설정 자체는 남는다. 항목 삭제 시 강조 영역에서도 제거한다.
- 목록 저장은 기존처럼 다른 일정·가계부 초안을 함께 공개하지 않는다. 두 사용자에게 동일한 중요 설정이 공유된다.
- 지정된 미완료 항목이 없으면 다른 항목을 대신 추천하지 않는다.

**저장 중 표시:** 원본 체크박스의 기존 낙관적 표시를 유지하되, 중요 항목은 저장 중에도 강조 영역에 ‘저장 중’ 상태로 남긴다. `pendingChecks`의 저장 전 상태와 진행 상태를 함께 반영해 성공 전에 항목이 사라지지 않게 한다. 실패하면 같은 항목의 오류·재시도를 유지한다. 원본 항목 이동 버튼은 원본 체크박스에 포커스와 스크롤을 이동하며, 항목 삭제·다른 탭 전환으로 대상이 없어지면 준비 제목 등 유효한 위치로 포커스를 보낸다.

### 4.5 가계부·설정·기타 화면

- 가계부 카테고리는 PC 별도 열, 모바일 항목 아래에 상시 표시한다.
- 입력·수정·삭제·순서 변경, 검색·카테고리·날짜 필터, 예산, 수동 환율, 통화별·카테고리별 합계, CSV를 유지한다.
- 저장·서버 갱신 중 추가 전 입력과 커서가 유지되는 기존 동작을 보존한다.
- 로그인, 자동 로그아웃, 버전 비교·복원, 초안 복구, 편집본 불러오기, 두 종류의 내보내기를 A안에 연결한다.
- 밝게·어둡게·기기 설정, 인쇄의 밝은 색상, PWA와 오프라인 작업본의 기존 정책을 유지한다.
- 기능 추가에 따른 설명은 필요한 곳에 짧게 표시한다. 개발·설정 상세를 일반 화면에 노출하지 않는다.

## 5. 데이터·호환성 설계

### 5.1 최소 확장안

구현 시작 시 아래 안을 기존 정제·저장·복원 경로에서 왕복 검증한다. 속성명은 제안이며 실제 구현에서 확정한다.

| 정보 | 저장 기본안 | 이전 데이터의 기본값 |
|---|---|---|
| 준비 중요 여부 | 준비 label의 검증된 `data-check-important="true"` | false |
| 숙소 표시 연결 | 원본 timeline-row의 검증된 숙소 표시 속성 | 비활성 |
| 숙박 종료일 | 같은 row의 `data-stay-checkout="YYYY-MM-DD"` | 미지정 |
| 숙박 시작일 | row가 속한 실제 일정 날짜 | 별도 복제하지 않음 |
| 숙소 카드·중요 항목 영역 | 원본에서 다시 만드는 화면 요소 | 저장하지 않음 |

원본 HTML 밖에 별도의 대규모 상태 모델을 도입하지 않는다. 다만 속성 추가만으로 호환성이 보장된다고 가정하지 않는다.

### 5.1.1 화면에서 참조할 상태

| 앱 상태 | 숙소·중요 영역의 기준 | 적용 시 주의 |
|---|---|---|
| 일반 온라인 조회 | 현재 화면에 적용된 공개본 | 알림만 받은 미적용 원격본과 섞지 않음 |
| 일정·가계부 초안 보유 | 현재 적용된 로컬 초안 | 원본 화면과 카드가 서로 다른 제목·사진을 보이지 않게 함 |
| 준비 목록 편집 창 | 창 안은 임시 목록, 본문은 창을 열기 전 적용 상태 | 중요 토글은 목록 저장 성공 후 본문에 반영 |
| 체크 저장 진행 | 적용 상태와 pendingChecks의 저장 전 값·진행 상태 | 중요 영역은 성공 전 유지, 실패 시 복구 |
| 버전 미리보기 | 현재 미리보기 버전 | 최신 공개본의 중요 표시·숙박 기간이 끼어들지 않음; 닫으면 원래 초안 복원 |
| 초안 복구 보류 | 현재 공개본 | 보관만 된 초안 내용을 강조 영역에 미리 표시하지 않음 |
| 오프라인 작업본 | 해당 파일에서 복구·적용된 로컬 상태 | 기본 trip-config나 온라인 공유본으로 대체하지 않음 |

숙소와 중요 영역을 그릴 때마다 별도 서버 조회를 하지 않는다. 기존 상태 적용 완료 지점에서 함께 갱신하고, 화면 상태·파생 DOM은 여행 데이터의 변경으로 판단하지 않는다.

### 5.2 함께 수정해야 하는 경로

1. `sanitizeMarkup()`에서 허용 요소·값을 검증한다. 잘못된 날짜·boolean·원본과 무관한 요소의 속성을 제거한다.
2. `checklistItems()`·`patchChecklist()`·`checklistShape()`에 중요 여부를 포함한다. 단순 체크, 목록 재정렬, 충돌 비교, 초안 병합 경로에서도 유지한다.
3. `captureState()`는 보조 영역·편집 도구를 저장에서 제외한다. 원본 체크박스만 수집하는지 확인한다.
4. `applyState()`·초안 복구·Realtime 갱신 후 보조 영역을 다시 만든다. 반복 적용해도 내용·DOM이 누적되지 않게 한다.
5. 일정 이동·삭제·복원 시 숙박 연결의 유효성을 다시 확인한다. 단순 렌더링으로 공유본을 자동 수정하지 않는다.
6. 버전·불러오기 비교에 중요 표시와 숙박 기간 변경을 설명한다. HTML만 달라졌다는 모호한 차이로 끝내지 않는다.
7. 오프라인 내보내기·불러오기에서 확장 정보를 보존한다. 인쇄·공유용 사본에서는 편집 도구를 제거하고 읽을 내용을 유지한다.
8. 생성 데이터에도 준비 ID·중요 여부와 숙박 연결을 필요한 범위로 전달한다. 서버 연결 정보·계정 정보는 초안 데이터에 넣지 않는다.

**추가로 확인할 실제 연결 지점:**

- `commitChecklistPatch()`는 서버 저장본뿐 아니라 `nextLocal`, `nextBase`, 실행 취소 이력에도 transform을 적용한다. 중요 표시가 이 경로 모두에서 보존되고 다른 초안이 공유 저장되지 않는지 검사한다.
- `stateSummary()`·`buildDiff()`가 읽는 항목에 신규 필드를 포함한다. 값만 바뀐 경우에도 변경이 0개로 계산되어 불러오기 버튼이 비활성화되지 않아야 한다.
- `sanitizeMarkup()`는 가계부 영역을 `moneyTemplateHtml`로 교체한다. A안 가계부는 새 문서뿐 아니라 과거 저장본을 적용할 때도 같은 최종 템플릿을 사용해야 한다.
- 보조 영역은 가능한 한 저장 대상 main 밖에 한 벌만 둔다. main 안에 둘 필요가 있으면 수집·정제 시 제거하고 적용 후 재생성한다. 편집 도구도 같은 원칙을 따른다.
- 의미가 같은 상태를 반복 적용·수집했을 때 정규화한 상태가 같아야 한다. 탭·날짜·테마·시간표 범위 이동과 파생 영역 갱신으로 `fingerprint()`가 달라지거나 초안이 생기지 않는지 검사한다.

### 5.3 스키마와 구형 앱에 대한 완료 조건

- schemaVersion 5 유지 또는 새 버전 도입은 1단계 호환성 실험 결과로 결정하고 근거를 기록한다. DB 스키마 변경과 문서 schemaVersion 변경은 별개다.
- 과거 저장본·기존 초안·구형 작업본을 열 때 일정·체크·가계부를 보존한다. 없는 신규 필드는 기본값으로 처리한다.
- 신규 필드가 없는 구형 작업본을 불러오거나 과거 버전을 복원하면 현재 중요 표시·숙박 기간이 사라질 수 있다. 차이 화면에 이를 표시하고 기존 적용·복원 확인을 거친다.
- 이미 열린 구형 앱은 중요 표시를 모른 채 목록을 다시 저장해 필드를 지울 수 있다. **버전 숫자만 올려 이 문제가 해결된다고 주장하지 않는다.** 두 사용자의 열린 앱 갱신과 구형 오프라인 파일 처리 절차를 운영 전환 조건에 포함한다.
- 코드 되돌리기도 같은 위험이 있다. 신규 데이터 저장 후에는 이전 코드가 신규 필드를 보존하는지 검증된 경우에만 편집 가능한 상태로 되돌린다. 그렇지 않으면 데이터 백업과 호환 수정이 우선이다.
- 해결에 서버 쓰기 제한 등 범위 확장이 필요하면 구체적인 위험·대안을 정리하고 확인받는다. 불확실한 상태로 운영 전환하지 않는다.

### 5.4 내보내기와 인쇄의 별도 처리

`exportStaticHtml()`은 앱 스크립트를 제거한 뒤 `appendReadonlyRuntime()`을 붙인다. 이 실행 코드는 현재 날짜 탭·사진 보기를 별도로 처리하므로 온라인 앱의 탐색만 바꾸면 읽기 전용 사본이 깨질 수 있다. 다음을 함께 구현·확인한다.

- 오프라인 작업본: 기본 설정과 상태를 파일 안에 포함하고 앱 초기화 후 숙소·중요 영역을 재생성한다. 저장 후 다시 연 파일에서도 중요 표시·숙박 기간이 유지되어야 한다.
- 인쇄·공유용 사본: 기존처럼 일별 일정 형식을 사용하며 시간표·편집·로그인·저장 기능은 제거한다. 바뀐 주 메뉴·날짜 선택이 읽기 전용 실행 코드에서도 동작하고 모든 날짜에 접근 가능해야 한다.
- 읽기 전용 사본의 날짜 변경에 따라 숙소를 바꿀 수 있는 최소 조회 코드를 포함하거나, 기존 일정 안의 숙소 정보로 전달한다. 동작하지 않는 숙소 카드·메뉴를 남기지 않는다. 최종 전달 방식을 단계 1에서 정하고 초안에서 검토한다.
- 중요 표시는 읽기 전용 사본에서도 확인 가능하고 체크는 변경할 수 없다. 사진·지도의 기존 내보내기 실패 정책을 유지한다.
- 인쇄 스타일은 PC 왼쪽 메뉴·모바일 고정 하단 메뉴·설정·진행 상태를 숨기고 기존 일별 일정 내용이 잘리지 않는지 확인한다.
- 생성한 두 종류의 HTML을 실제 새 브라우저 context에서 열어 확인한다. 온라인 화면 캡처만으로 파일 기능 검증을 대신하지 않는다.

## 7. 단계별 실행과 산출물

단계 1의 호환성 결정 후 단계 2의 화면 검토를 거쳐 단계 3~4의 운영 기능 통합을 진행한다. 단계 3~4는 일정·준비·가계부 순으로 검증 가능한 작은 변경 단위로 나눈다. 각 단위는 관련 검사와 문서 갱신까지 포함하고, 최종 단계에서 한꺼번에 호환성 문제를 발견하는 방식으로 진행하지 않는다.

### 구현 시작 시 확정할 기술 결정

아래 결정은 현재 요구사항 안에서 코드·검사 근거로 해결한다. 기능 축소, 저장 정책 변경 또는 서버 변경이 필요한 경우에만 사용자에게 확인한다. 단순 구현 선택마다 재승인을 요청하지 않는다.

| 결정 | 확인할 근거 | 결정 시점 |
|---|---|---|
| 필드·스키마 버전 | 구형 자료 왕복, 문서 버전 검증, 정규화·캐시·초안 복구 | 단계 1 완료 전 |
| 저장 영역과 파생 영역 위치 | main 교체·정제·fingerprint 및 기존 선택자 | 단계 1 완료 전 |
| 읽기 전용 사본의 숙소 전달 방식 | 날짜 전환, 앱 스크립트 제거 후 동작, 사진 포함 | 단계 2 완료 전 |
| 기능 통합 검토본의 생성·시험 경로 | main 자동 배포와 분리, 가상 API 사용, 같은 후보 코드 검증 | 단계 3 시작 전 |

각 결정은 이 문서에 선택·이유·검증 근거를 짧게 기록한다. 별도의 설계 문서 체계를 새로 만들지 않는다.

### 단계 1 — 기능 목록과 저장 호환성 확인

2026-10-23 결정: 문서 스키마 5를 유지한다. `data-check-important="true"`와 원본 일정의 `data-stay-checkout`만 추가한다. 체크아웃 속성이 숙소 지정 여부도 나타내므로 별도 boolean을 중복 저장하지 않는다. `main` 밖의 `#daylightContext`를 현재 적용 DOM에서 다시 만들고 저장 대상에서는 제외한다. 중요 표시를 목록 shape·patch·diff에 포함한다. 읽기 전용 사본은 숙박 종료일을 원본 일정에 표시하고 기존 날짜 탭으로 모든 날짜를 탐색한다. 기존 앱은 신규 필드를 지울 수 있으므로 버전 숫자가 보호 장치가 되지는 않는다. 두 사용자의 앱 갱신과 구형 작업본 정리가 운영 전환의 선행 조건이다.

| 기존 기능 | 후보의 연결 지점 |
|---|---|
| 일정·준비·가계부 | 하나의 주 메뉴와 기존 날짜 radio·panel, PC 왼쪽/모바일 하단 |
| 일정 편집·시간·분류·사진·지도·주의사항 | 기존 원본 카드·대화상자, 숙박 기간 버튼 추가 |
| 준비 체크·목록 저장·동시 편집 | 기존 인증·revision patch 유지, 목록 편집에 중요 토글 |
| 가계부·합계·필터·CSV·설정 | 기존 함수·최종 money 템플릿 유지, 카테고리 상시 표시 |
| 저장·실행 취소·초안·오류 | 본문 위 편집 도구와 항상 보이는 상태 안내 |
| 버전·로그아웃·가져오기·내보내기·테마 | 설정의 편집과 저장 / 파일 / 화면 그룹 |
| 시간표·상세·키보드 | 기존 계산과 상세 창 재사용, 날짜 선택을 주 탐색과 동기화 |
| 오프라인·읽기 전용 | 기존 내보내기 실행 코드 유지, 실제 파일 재실행 검사 추가 |

기능 통합 검토본은 `scripts/build-daylight-review.mjs`가 후보 `index.html`에서 생성한다. 합성 fixture만 사용하며 운영 API·계정·PWA 등록을 제거하고 고유 tripId·캐시 이름으로 분리한다. 공개본은 오프라인 모드로 로컬 편집을 보여주며 실제 공유 저장과 충돌은 동일 후보의 로컬 가상 API 검사에서 확인한다. 식별값은 기준 커밋·후보 소스 SHA-256·fixture 버전이다.

- 사용자 안내서의 기능을 A안 화면·버튼에 대응시킨다. 기존 DOM 선택자와 이벤트 연결 지점을 확인한다.
- 최소 fixture로 중요 표시·숙박 기간을 저장 → 적용 → 다시 수집하는 실험을 한다.
- 체크만 변경하거나 목록을 저장해도 중요 표시가 보존되는지 확인한다.
- 기존 저장본·초안·오프라인 파일의 입력 형식과 버전 정책을 확정한다.
- 기존 내보내기 파일을 기준 fixture로 확보하고 온라인·오프라인·읽기 전용 실행 코드의 탐색 의존성을 정리한다.
- **산출물:** 기능 대응표, 확정 필드·스키마 결정, 호환성 검사, 구형 앱 전환 조건.
- **완료 기준:** 화면 변경 후에도 무엇을 저장하고 어떻게 복원하는지 검증 가능하며 기능 누락이 없다.
- **선행 검사:** 기존 주요 검사 결과와 기준 커밋을 기록하고, 이미 있던 실패는 신규 변경의 실패와 구분한다. 기존 미커밋 문서 변경도 작업 범위에 기록해 보존한다.

### 단계 2 — 초안 보완과 공개 검토

- 날짜별 숙소·중요 준비 항목을 예시 데이터로 구현한다. 실제 서버 쓰기는 연결하지 않는다.
- 여행 전·중·후, 빈 목록, 중요 항목 모두 완료, 숙소 없는 날을 확인한다.
- PC 편집 화면과 모바일 조회 화면, 설정·오류·저장 중 상태를 검토 가능하게 만든다.
- 캡처·초안 검사를 수행하고 공개 생성물을 만든다. 승인된 초안 배포 범위에서 HTTPS 검토 주소를 제공한다.
- **산출물:** 동작하는 A안 초안, PC·모바일 캡처, 연결 전 기능의 명확한 표시.
- **완료 기준:** 사용자가 원격에서 화면과 흐름을 검토할 수 있고 B/C와 운영 앱에 영향이 없다.

### 단계 3 — 운영 앱에 화면 골격 적용

- 운영 코드 기반의 작업본에서 A안 탐색·레이아웃·색상·테마를 적용한다.
- 후보 코드는 별도 `codex/` 브랜치 등 운영 배포와 분리된 작업 상태에서 관리한다. 필요하면 기존의 적절한 worktree를 재사용한다. 승인 전 운영 루트 `index.html` 변경을 main에 배포하지 않는다.
- 원본 일정·준비 DOM을 보존하고 보조 영역을 저장 데이터와 분리한다.
- 기존 저장본을 적용한 뒤에도 A안 화면이 유지되는지, 편집·복구가 동작하는지 확인한다.
- **산출물:** 기존 데이터로 열리는 운영 기능 통합 작업본.
- **완료 기준:** 저장 전후 핵심 내용이 같고, 화면 이동만으로 미저장 상태가 생기지 않는다.

### 단계 4 — 실제 기능 연결

1. 일정·시간표·날짜별 숙소 및 일정 편집을 연결한다.
2. 준비 중요 표시, 원본 항목 이동, 완료·실패·재시도를 연결한다.
3. 가계부 입력·필터·합계·설정·저장을 연결한다.
4. 인증·세션 종료·초안·충돌·버전·파일·테마를 새 UI에서 확인한다.
5. 하드코딩된 날짜·시각·도시·가상 지출·체크 수를 제거한다.

- **산출물:** 필수 기능이 연결된 A안 앱과 기능별 회귀 근거.
- **완료 기준:** 각 기능이 사용자 안내서의 저장·권한 정책을 유지한다. 운영 후보에 배치 검토용 비활성 버튼이 남지 않는다.

### 단계 5 — 통합 검증과 문서 정리

- 아래 검증표와 기존 자동 검사를 실행한다. 실패를 숨기기 위해 기존 검사를 삭제·완화하지 않는다.
- 실제 렌더링으로 글자 크기·넘침·포커스·다크 테마·인쇄를 확인한다.
- 안내서를 최종 구현과 비교하고 새 기능 사용법과 이전 버전 처리 절차를 반영한다.
- **산출물:** 검증 결과, 알려진 제한, 갱신된 문서, 운영 전환 후보.
- **완료 기준:** 데이터 손실·기존 기능 퇴행 문제가 없고, 검증하지 못한 범위가 명시되어 있다.

### 단계 6 — 운영 전환 검토와 배포

- 운영 쓰기가 발생하지 않는 검토본을 공개 HTTPS로 제공한다. 실제 기능 검토에는 가상 API 또는 격리된 테스트 데이터를 사용한다.
- 별도 검토 경로는 운영 PWA와 다른 scope를 사용하거나 PWA 등록을 끈다. 어느 경우든 가상 tripId·저장소 네임스페이스·인증 저장 키를 운영과 분리한다. PWA를 끄는 것만으로 IndexedDB·인증 세션이 분리된다고 가정하지 않는다. 운영 계정·실제 여행 내용을 테스트 fixture에 복사하지 않는다.
- 시각 초안은 기존 생성기를 사용한다. 기능 통합 검토본은 후보 소스에서 재현 가능하게 생성하고, 독립된 앱을 수동 복사해 유지하지 않는다. GitHub Pages만으로 로그인·공유 저장을 가상 구현할 수 없으므로 공개본에는 동작 범위를 표시하고, 저장·충돌·복구는 같은 후보 소스를 가상 API에 연결한 브라우저 검사 근거로 검토한다. 완전한 대화형 공개 기능 검토가 필요하면 격리 환경 준비 범위를 먼저 정한다.
- 검토본 식별값에는 후보 커밋과 fixture 버전을 기록한다. 운영 전환 때 후보와 달라진 부분이 있다면 관련 검사를 다시 수행한다.
- 화면 검토, 기능 검증, 구형 앱 갱신·복귀 계획이 준비된 결과로 운영 적용 승인을 받는다.
- 승인 뒤 검증된 변경만 배포하고 실제 배포 상태·공개 자원·서비스 워커 갱신을 확인한다.
- **완료 기준:** 두 사용자가 새 앱에서 기존 데이터와 신규 설정을 확인할 수 있으며 이전 창·구형 작업본 처리 안내가 준비되어 있다.

검사 방법은 [운영 안내서의 검증 절차](OPERATIONS_KO.md#validation)를 따른다. 단계별로 관련 검사를 실행하고 통합 완료 시 `npm test`, `npm run test:browser`, 초안 검사 및 `git diff --check`를 수행한다. npm이 없을 때의 대체 실행도 운영 안내서를 따른다. SQL·권한을 변경하지 않았다면 UI 변경만을 이유로 SQL 실행 검사를 새로 확대하지 않는다.

기존 CI의 SQL 검사는 유지한다. `.github/workflows/validate.yml`은 현재 단위·SQL 검사에 Node 24, 브라우저 검사에 Node 22를 사용한다. 로컬 Node 24의 결과만으로 브라우저 CI도 통과했다고 판단하지 않고, 후보 커밋의 CI 최종 결과를 확인한다.

### 검사와 구현 단위의 대응

| 변경 | 주요 기존 검사와 추가 범위 |
|---|---|
| 준비 중요 표시·저장 | `scripts/check-prep-browser.mjs`에 중요 여부만 변경·체크 대기·동시 변경 검사 추가 |
| 상태·초안·충돌 | `scripts/check-drafts-browser.mjs`·`check-storage-browser.mjs`에서 다른 초안 비공개와 이력 보존 확인 |
| 버전·가져오기·내보내기 | `scripts/check-imports-browser.mjs`를 바탕으로 메타데이터만의 차이, 구형 파일, 생성 HTML 실행 검사 추가. 별도 검사가 필요하면 작은 단위로 작성하고 브라우저 실행 목록에 등록 |
| 시간표·숙박 날짜 | `tests/timetable.test.mjs`의 기존 시간 의미 유지, 숙박 기간 선택은 별도 순수 처리로 경계 검사 |
| 인증·가계부·사진 | `scripts/check-auth-browser.mjs`·`check-ledger-browser.mjs`·`check-photos-browser.mjs`의 사용자 동작 유지 |
| 테마·PWA | `tests/theme.test.mjs`·`tests/pwa.test.mjs`와 대응 브라우저 검사에서 새 화면·출력 동작 확인 |
| 전체 구조·설정 | `scripts/check-project.mjs`·`tests/project.test.mjs`의 설정·문서 정합성 및 신규 필드 검증 갱신 |

검증 기록에는 후보 커밋(미커밋 변경이 있으면 함께 명시), 런타임, 실행 명령, 합격·실패, 미검증 항목, 관련 캡처·진단 자료의 참조를 포함한다. 민감한 내용이 포함된 실제 여행 스냅샷을 공개 검증 자료로 올리지 않는다.

순수 날짜 선택·중요 항목 필터·메타데이터 왕복에는 의미 있는 단위 검사를 추가하고, 저장·충돌·복원은 실제 브라우저 흐름으로 검사한다. DOM 선택자는 새 UI에 맞춰 바꿀 수 있지만 기존 검사의 사용자 관점 단언은 유지한다. 실제 휴대폰 키보드·브라우저 강제 다크모드 등 자동 검사 밖의 항목은 미검증 여부를 따로 적는다.

## 9. 배포와 복귀 조건

- 운영 검증에서 실제 공유본을 시험 데이터로 덮어쓰지 않는다. 최종 공개본·revision과 필요한 백업을 확인한 뒤 승인된 데이터 변경만 수행한다.
- 코드 배포와 여행 데이터 저장은 별개다. 설정 파일 수정·Git push를 공유 데이터 갱신으로 보고하지 않는다.
- 새 메타데이터를 저장하기 전에 구형 열린 앱과 코드 되돌리기의 영향을 검증한다. 복귀 시 실제 여행 지출·일정을 과거 백업으로 일괄 덮어쓰지 않는다.
- 커밋·푸시가 승인된 경우 저장소 AGENTS.md의 Windows Git 권한 규칙을 따른다. 완료 보고는 status·마지막 commit·추적 branch·remote를 확인하고 한다.
- Pages 배포 완료와 공개 주소에서의 실제 동작을 확인한다. 기존 인계에 적힌 배포·테스트 성공을 이번 결과로 재사용하지 않는다.
