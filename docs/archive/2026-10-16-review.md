#### 1. 높은 우선순위: 초안 복구 후 체크리스트 저장 시 충돌 보호 우회

**상태: 실제 Chromium과 로컬 가상 서버에서 재현 완료.**

관련 코드:

- `index.html:2402` — `recoverOnlineDraft()`
- `index.html:2420` — 복구 시 `publishedRevision`만 과거 초안의 값으로 변경
- `index.html:1736` — `commitChecklistPatch()`
- `index.html:1770` — `nextBase`와 서버 저장 결과가 같으면 최신 revision을 채택

##### 원인

페이지 로딩 시 `lastSavedState`에는 최신 서버 상태가 들어간다. 이후 과거 초안을 복구하면 화면은 과거 초안으로 바뀌고 `publishedRevision`도 과거 값으로 바뀌지만, `lastSavedState`는 최신 서버 상태로 남는다. 즉 기준 내용과 revision이 서로 다른 시점을 가리킨다.

이 상태에서 체크리스트를 저장하면 최신 기준 내용에 체크 변경을 적용한 `nextBase`가 서버 저장 결과와 같으므로 최신 revision을 채택한다. 그러나 화면의 다른 데이터는 여전히 과거 초안이다. 이후 전체 저장은 최신 revision으로 성공하여 상대방 변경을 충돌 안내 없이 덮어쓴다.

##### 재현 절차

1. 서버 revision 1, 예산 0원인 상태를 연다.
2. 일정 제목을 수정하고 초안을 브라우저에 보관한다. 서버에는 저장하지 않는다.
3. 다른 사용자가 서버 예산을 987,654원으로 수정하여 revision 2로 저장한다.
4. 첫 사용자가 새로고침하고 이전 초안을 복구한다.
5. PREP 체크박스 하나를 변경하여 즉시 저장한다.
6. 첫 사용자가 전체 초안을 저장한다.

##### 실제 관측 결과

```text
복구 직후: local budget=0, base budget=987654, revision=1
체크 저장 후: local budget=0, base budget=987654, revision=3
서버 예산은 체크 저장 직후까지 987654
전체 저장 후: server budget=0, revision=4, conflict dialog=false
브라우저 JavaScript 오류 없음
```

##### 최소 수정 방향

복구된 초안의 기준 내용과 revision을 일치시킨다. 초안 레코드의 `baseState`와 `baseRevision`을 함께 복원하는 방향을 검토하되, 현재 최신 서버 상태도 충돌 비교에 사용할 수 있도록 유지한다. 구형 초안에 `baseState`가 없는 경우도 고려한다. 단순히 revision만 최신으로 바꾸면 안 된다.

회귀 검증: 위 재현에서 체크 저장 자체는 성공하되, 이후 전체 저장은 상대방의 예산 변경을 조용히 덮어쓰지 않아야 한다. 최신 내용이 보존되거나 충돌 확인이 필요하다.

#### 2. 높은 우선순위: 복구 안내에서 Esc를 누르면 초안 삭제

**상태: 실제 Chromium에서 재현 완료.**

관련 코드:

- `index.html:1981` 부근 — `closeTopDialog()`는 일반 안내창의 Esc를 `cancel`로 처리
- `index.html:2410` — `recoverOnlineDraft()`의 `if(choice!=='restore')` 분기

##### 재현 절차

1. 일정 제목을 수정하고 초안 저장을 기다린다.
2. 새로고침한다.
3. “저장하지 않은 초안을 찾았습니다.” 안내창에서 Esc를 누른다.
4. IndexedDB 초안이 삭제되고 원래 제목으로 돌아간다.

실제 관측: `draftStillExists=false`. 명시적인 “초안 삭제” 선택은 하지 않았다.

##### 최소 수정 방향

`discard`를 명시적으로 선택한 경우에만 삭제한다. `cancel`, 다른 안내창으로 교체되는 `replaced` 등의 응답은 초안을 보존하도록 별도 처리한다. 취소 후 페이지 초기화 과정이나 후속 dirty 상태 정리가 보관한 초안을 다시 삭제하지 않는지도 확인한다.

회귀 검증: 복구 안내의 Esc와 명시적 삭제를 각각 검증한다. 기존 로그아웃 취소 테스트만으로는 이 문제를 잡지 못한다.

#### 3. 중간 우선순위: 한 기기의 로그아웃이 다른 기기 세션에 영향

**상태: 앱 코드와 설치된 SDK 소스로 확인. 실제 운영 계정 로그아웃은 수행하지 않음.**

관련 코드:

- `index.html:1999` — `signOutEditor()`에서 `client.auth.signOut()` 호출
- `node_modules/@supabase/auth-js/src/GoTrueClient.ts:4054` — 기본 옵션 `{ scope: 'global' }`

현재 여행은 편집자 이메일 하나와 여행별 편집자 한 명을 사용하는 구조다. 두 사람이 같은 계정으로 편집한다면, 한 기기의 30분 자동 로그아웃이 다른 기기의 refresh token도 해제할 수 있다. 이미 발급된 access token은 만료 전까지 유효하므로 모든 화면이 즉시 로그아웃된다는 의미는 아니다. 이후 세션 갱신에 문제가 생길 수 있다.

##### 최소 수정 방향

일반 수동·자동 로그아웃에 `client.auth.signOut({ scope: 'local' })`을 사용한다. 같은 브라우저 탭 간 동기화는 기존 BroadcastChannel/storage 흐름을 유지한다. 이 문제만 해결하기 위해 다중 사용자 권한 체계를 새로 만들 필요는 없다.

#### 4. 중간 우선순위: 전체 일정 저장에 제한 시간 없음

**상태: 코드 검토로 확인한 잠재 문제. 네트워크 정지 상황의 별도 브라우저 재현은 수행하지 않음.**

관련 코드:

- `index.html:2030` — `persistState()`
- `index.html:2043` — `save_trip_document` RPC 요청
- 비교 대상: `fetchPublishedState()`는 8초 제한, `commitChecklistPatch()`의 저장 RPC는 12초 제한

전체 일정 저장 RPC에는 앱 자체 제한 시간이 없다. 응답이 멈추면 저장 중 상태가 장시간 유지될 수 있다. 이 단계에서는 `cancelable:false`로 설정되어 취소 버튼도 제공하지 않는다. 요청 이후 상태 해제도 전체 `try/finally`로 보호되어 있지 않다.

##### 최소 수정 방향

기존 체크리스트 저장과 같은 AbortController 제한 시간 및 `finally` 정리를 적용한다. 실패 시 초안을 유지한다. 시간 초과가 서버 저장 실패를 뜻하는 것은 아니므로, 최신 revision과 내용을 다시 조회하여 저장 여부를 확인하고 재시도하도록 한다. 무조건 자동 재저장은 피한다.
