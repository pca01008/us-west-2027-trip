# A안(Daylight) 후속 논의 인계

## 다음 세션에서 먼저 읽을 내용

사용자는 세 초안 중 **A · Daylight를 기반으로 논의를 이어가기로 선택했다.** 다음 세션은 A안의 개선 논의부터 재개한다. 세 방향을 다시 고르는 단계로 돌아가거나 운영 앱에 즉시 적용하는 것으로 해석하지 않는다.

사용자의 마지막 요청:

> A버전으로 논의를 이어나가려 해. 다음 세션에서 진행할 수 있도록 필요한 내용을 md 파일로 저장해줘. git commit도 해주고.

## 확정된 사항과 미확정 사항

| 구분 | 내용 |
|---|---|
| 목표 | UI를 원점에서 검토하여 실제 상업 서비스 수준의 완성도로 발전 |
| 선택한 기반 | A · Daylight |
| 사용 장면 | 여행 전 PC에서 계획·예산 편집, 여행 중 휴대폰 조회를 **같은 비중**으로 고려 |
| 사용자 규모 | 여행 참가자 두 명. 기존 패턴·의존성을 활용하고 유지보수 부담을 작게 유지 |
| 아직 결정하지 않은 것 | A안 세부 수정, 운영 화면 적용 범위·순서, 최종 디자인 토큰, 편집·저장·오류 상태의 배치 |
| 승인되지 않은 제안 | 이전 답변에서 제안한 “A 기반에 C의 3일 비교 결합”은 추천일 뿐이다. 사용자는 A만 선택했으며 C 결합을 승인하지 않았다. |

A안의 모든 문구·여백·색상·예시 상태를 최종 확정한 것은 아니다. B/C는 비교 기록으로 보존하고 기본 진행 방향은 A로 둔다.

## A안이 제안하는 구조

- PC: 왼쪽에 일정·준비·가계부 메뉴, 중앙에 날짜 선택과 일별 일정, 오른쪽에 숙소·준비 요약.
- 모바일: 상단 헤더를 작게 두고 일정을 먼저 표시. 일정·준비·가계부는 하단 고정 탐색으로 이동.
- 세이지 바탕과 짙은 녹색 강조, 흰 표면, 얇은 구분선. 큰 장식 헤더와 중첩 카드·그림자의 비중을 줄임.
- 시간·일정명·장소는 바로 읽고 주의 사항은 펼쳐서 확인. 날짜 선택과 기능 메뉴를 별도 단계로 분리.
- 시계와 관리 도구의 비중을 낮추고 일정 내용을 중심에 둠.

이는 논의를 위한 방향 설명이다. 최종 디자인 시스템 문서 `DESIGN.md`나 영구 토큰 계약은 아직 없다.

## 프로토타입의 한계 — 운영 기능으로 오해하지 않기

날짜 이동, 메뉴 전환, 준비 체크, 주의 사항 펼치기, 지출 필터와 지도 링크만 체험할 수 있다. 준비 체크는 현재 페이지 메모리에서만 유지된다.

첫 화면은 2027년 1월 25일 여행 중 상황을 가정한다. 시각, 다음 일정 강조, 준비 완료 상태와 지출 3건은 예시다. 숙소 패널·여행 문구에도 고정값이 있으므로 실제 날짜·일정에 반응하는 운영 동작으로 간주하지 않는다.

편집·인증·서버 저장·버전 관리·시간표·오프라인·내보내기·다크 테마는 초안에 연결되지 않았다. 기능을 없애기로 결정한 것이 아니다. A안 적용 시 기존 기능과 데이터 무결성을 유지해야 한다. 실제 동작은 [사용자 안내서](../USER_GUIDE_KO.md), 내부 구조는 [기술 설명서](../PROJECT_GUIDE_KO.md)가 기준이다.

## 다음 논의의 권장 순서

1. A안을 함께 보며 마음에 드는 부분과 불편한 부분을 먼저 확인한다. 특히 글자 크기·정보 밀도·PC 보조 패널·모바일 하단 탐색을 중심으로 의견을 모은다.
2. 여행 전·중·후의 첫 화면과 날짜 이동 방식을 구체화한다. 고정된 1월 25일 예시 화면이 실제 날짜 처리의 요구사항을 대신하지 않게 한다.
3. 조회와 편집을 어떻게 나눌지 논의한다. 저장·미저장·실패·복구 안내와 관리 도구를 간결하면서도 놓치지 않게 배치한다.
4. 준비·가계부·시간표·사진·다크 테마 등 나머지 화면을 A의 언어로 확장할 범위를 정한다. C의 비교 보드는 사용자가 다시 원할 때만 채택을 논의한다.
5. 구체적인 적용 요청이 나오면 기존 운영 구조에 맞춘 변경 계획을 세우고, 관련 동작의 회귀 검증 범위를 정한다. 프로토타입 파일로 운영 앱을 통째로 교체하지 않는다.

위 순서는 제안이며 추가로 확정된 사용자 요구사항은 아니다. 이번 요청의 범위는 인계 문서 저장과 Git 커밋이다.
