# 2026-10-19 테스트 관점 프로젝트 검토

이 문서는 2026-10-19 코드 검토와 로컬 테스트 실행 결과를 보존한다. 이후 구현이나 운영 환경의 상태를 보증하지 않는다. 아래 항목은 테스트 보강 제안이며, 해당 기능의 버그가 재현되었다는 뜻은 아니다.

## 결론과 작업 범위

현재 초안 복구·저장 충돌·사진 통신 실패 테스트는 충실하다. 실제 DB 검증과 비정상 입력·저장소 장애 검증을 우선 보강하는 것이 좋다.

- 검토 대상: 앱 코드, SQL, 단위·브라우저 검사, CI와 관련 문서.
- 검토 단계에서는 코드 수정이나 운영 데이터 변경 없이 검사만 수행했다.
- 사용자 요청에 따라 이 기록을 저장하고 README에 링크를 추가했다.
- 제안한 테스트 추가, 앱 수정, 배포, 커밋·푸시는 수행하지 않았다.
- 실행 절차의 기준 문서는 [운영 안내서](../OPERATIONS_KO.md#validation)다. 이 문서는 검토 당시의 결과와 후속 검증 항목을 기록한다.

## 실행 결과

| 검사 | 관측 결과 |
|---|---|
| `node --test tests/*.test.mjs` | 114개 통과, 실패·건너뜀 없음 |
| `node scripts/check-project.mjs` | 통과: 11일, 36개 일정, 12개 체크 항목 |
| `node scripts/check-browsers.mjs` | 초안·입력·PREP·사진·테마·PWA 6개 검사 묶음 모두 통과 |

실행 환경은 Windows, Node.js 24.19.0, 설치된 Chrome 155.0.8059.80이다. 브라우저 검사에는 `PWA_BROWSER_CHANNEL=chrome`을 사용했다. npm이 셸에서 인식되지 않아 제공된 Node 실행 파일로 해당 스크립트를 직접 실행했다.

최초 샌드박스 실행에서 단위 HTTP 검사 2개가 실패했고, 브라우저 실행도 기본 Playwright 브라우저 경로 부재와 localhost 연결 차단을 만났다. 설치된 Chrome으로 연결 차단(`ERR_NETWORK_ACCESS_DENIED`)을 확인한 뒤, 승인된 샌드박스 밖 실행에서 전체 검사가 통과했다. 이를 앱 결함으로 판정하지 않았다.

브라우저 검사는 로컬 모의 서버를 사용하며 운영 API 접근을 차단한다. 따라서 이 결과는 운영 DB 권한·실제 인증 서비스·실기기의 정상 동작을 직접 확인한 결과가 아니다.

## 우선순위별 개선 항목

### 1. 저장·권한 SQL 실행 테스트 — 높음

쉽게 말하면, 실제 데이터 창고에서도 허용된 사람만 저장하고 두 기기의 저장이 서로 덮어쓰지 않는지 확인하는 것이다.

현재 [프로젝트 테스트](../../tests/project.test.mjs)의 SQL 검사는 주로 문자열을 확인한다. [초안 브라우저 검사](../../scripts/check-drafts-browser.mjs)는 revision 검사를 구현한 모의 서버를 사용한다. [기존 SQL 실행 검사](../../scripts/check-db-health-sql.mjs)는 DB 상태 점검 테이블을 대상으로 하므로 앱의 저장 함수와 권한을 검증하지 않는다.

격리된 DB에서 [서버 SQL](../../supabase_setup.sql)과 [여행 등록 SQL](../../register_trip.sql)을 실행하고 다음을 확인한다.

- 익명·비편집자·다른 여행 편집자의 저장과 비공개 버전 조회를 차단한다.
- 문서 직접 수정은 차단하고 허용된 편집자의 저장 함수 호출만 성공한다.
- 같은 revision으로 동시에 저장하면 하나만 성공하고 다른 요청은 충돌한다. 실제 동시성 검증은 별도 연결을 사용한다.
- 충돌·잘못된 문서·용량 초과로 실패하면 문서와 버전 이력이 변하지 않는다.
- 정상 저장은 revision을 한 번 올리고 해당 여행의 버전을 최신 50개로 유지한다. 다른 여행은 영향을 받지 않는다.
- 신규 설치·기존 구조 업그레이드·SQL 재실행에서 일정과 편집자 연결을 보존한다.
- 사진 경로·여행별 업로드 권한과 덮어쓰기·삭제 제한을 확인한다. Storage 서비스까지 포함하는 검증은 DB 정책 검사와 구분한다.

### 2. 가져오기·정제·구버전 호환 테스트 — 높음

쉽게 말하면, 잘못되거나 오래된 백업 파일을 열어도 현재 일정이 망가지지 않는지 확인하는 것이다.

[앱](../../index.html)의 `readImportFile`, `sanitizeMarkup`, `normalizeState`, `migratePublishedState`에는 여행 ID·버전 검사와 데이터 정제 로직이 있다. 현재 검사는 정상 파일과 일부 가져오기 흐름을 다루지만 비정상 파일을 실제 파일 입력으로 넣는 검증은 부족하다.

- 다른 여행 파일, 미래 버전, 버전·편집 데이터 누락, 깨진 JSON을 넣고 거부 및 기존 초안 보존을 확인한다.
- 중복 일정·체크·사진 ID, 잘못된 숫자, 스크립트·이벤트 속성·위험 URL을 넣고 정제 결과를 검증한다.
- 위험한 동작이 실행되지 않는 동시에 정상 일정·링크·사진은 유지되는지 확인한다.
- 구버전 문서 fixture에서 일정 내용·체크 상태·안정적인 식별자 보존을 확인한다.
- 비교 화면을 연 뒤 서버 revision이 바뀌면 다시 비교하고 사용자 확인 없이 적용·저장하지 않는지 검사한다.

### 3. IndexedDB 장애 테스트 — 높음

쉽게 말하면, 휴대전화의 임시 저장 공간이 꽉 차거나 저장이 중단됐을 때 작성 중인 내용을 어떻게 보호하는지 확인하는 것이다.

[PREP 검사](../../scripts/check-prep-browser.mjs)는 저장 함수를 실패하도록 대체한다. 이는 실패 후 화면 동작을 확인하지만 실제 `openDraftDatabase`, `writeDraftRecord`, `clearDraftRecord`의 장애 처리를 검증하지는 않는다.

- DB 열기 실패, 용량 초과, 쓰기 트랜잭션 중단, 삭제 실패를 각각 주입한다.
- 실패 안내, 메모리 내 편집 유지, 저장·내보내기 가능 여부, 재시도 결과를 확인한다.
- 삭제 실패를 성공으로 표시하거나, 이전에 저장된 초안을 조용히 잃는 일이 없는지 확인한다.
- 영구 저장에 실패한 내용이 새로고침 후에도 복구된다고 가정하지 않는다. 실제로 보존된 데이터와 사용자 안내가 일치해야 한다.

### 4. 가계부 계산·CSV 결과 테스트 — 중간

쉽게 말하면, 항목을 입력할 수 있는지에 더해 합계와 내려받은 파일의 숫자도 맞는지 확인하는 것이다.

[현재 프로젝트 검사](../../tests/project.test.mjs)는 가계부 필터·CSV·필수 카테고리 관련 코드 존재를 주로 확인한다. 입력 보존 브라우저 검사는 있지만 계산과 CSV 출력의 의미를 검증하는 사례는 부족하다.

- 원화·달러 혼합 합계, 환율 변경, 소수점 반올림을 고정된 기대값과 비교한다.
- 예산 미설정·초과, 빈 목록, 삭제된 카테고리를 확인한다.
- 날짜·카테고리·검색 필터의 조합과 CSV에 포함되는 행이 일치하는지 확인한다.
- CSV의 쉼표·따옴표·줄바꿈·한글·수식 시작 문자 처리를 실제 내려받은 내용으로 검증한다.

### 5. 실제 SDK를 통한 인증 흐름 검증 — 중간

쉽게 말하면, 테스트용 가짜 로그인에서 생략한 실패·만료 상황도 확인하는 것이다.

[초안 검사](../../scripts/check-drafts-browser.mjs)와 [PREP 검사](../../scripts/check-prep-browser.mjs)의 인증 모의 구현은 로그인 성공으로 고정되며 `onAuthStateChange` 구독도 비어 있다. 로그아웃 후 앱의 보호 동작을 검증하더라도 실제 SDK 이벤트 연결까지 확인한 것은 아니다.

- 잘못된 비밀번호, 인증 서버 장애, 비편집자 세션을 검증한다.
- 토큰 갱신·만료·외부 로그아웃 이벤트가 앱 상태에 전달되는지 확인한다.
- 실패 후 재시도 가능 여부와 기존 초안 보존을 확인한다.
- 실제 SDK와 로컬 모의 API를 연결한 소수의 테스트를 추가하고, 운영 계정으로 실행하는 검증과 구분한다.

### 6. 실패 진단 자료 개선 — 중간

쉽게 말하면, 테스트가 실패한 순간의 화면과 진행 기록을 남겨 원인을 빨리 찾도록 하는 것이다.

[CI](../../.github/workflows/validate.yml)에 자료 업로드는 있지만 스크린샷은 일부 정상 진행 지점에서만 생성된다. 특히 초안 검사는 실패 시 화면·trace를 저장하는 처리가 없다. 기존 자료만으로 실패 순간을 확인하기 어려울 수 있다.

- 실패한 시나리오 이름, 스크린샷, 콘솔·요청 오류, trace를 남긴다.
- 종료 전에 진단 자료를 저장하고 CI 업로드 경로와 일치시킨다.
- 자료에는 모의 데이터만 사용한다. 실제 로그인 토큰이나 개인 여행 데이터를 포함하지 않는다.
- 문자열 일치 검사는 배포 설정 등 필요한 곳에 유지하되, 중요한 사용자 동작은 실행 결과 검증으로 보완한다.

## 실제 기기 확인과 권장 진행 순서

현재 모바일 브라우저 검사는 모두 Chromium의 화면 크기·터치 모의 실행이다. 실제 iPhone Safari나 삼성 인터넷에서 실행한 결과는 아니다.

두 사용자의 실제 기기에서 로그인 → 사진 추가 → 저장 → 초안 복구 → 오프라인 재실행을 배포 전에 확인한다. Safari를 사용한다면 핵심 흐름만 WebKit 자동 검사에 추가하는 정도가 적절하다.

권장 순서는 다음과 같다.

1. DB 저장·권한 실행 테스트와 가져오기·정제 검증을 보강한다.
2. IndexedDB 장애와 가계부 계산·CSV 검증을 추가한다.
3. 인증 SDK 흐름과 실패 진단 자료를 보완한다.

두 명이 사용하는 프로젝트 규모에 맞춰 기존 Node·Playwright 검사 구조를 우선 활용한다. 전체 프레임워크 교체나 광범위한 기기 조합 검사부터 도입할 필요는 없다. 테스트를 실제 추가하는 작업에서는 최종 구현에 맞춰 [운영 안내서의 검증 범위](../OPERATIONS_KO.md#validation)도 갱신한다.
