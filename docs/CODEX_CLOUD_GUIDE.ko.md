# 현재 프로젝트의 Codex Cloud 작업 가이드

작성일: 2026-10-26. 사용자의 요청으로 이 문서만 한국어로 작성했습니다.

이 문서는 `pca01008/us-west-2027-trip`을 Codex Cloud에서 개발하는 절차를 설명합니다. 실제 클라우드 환경 생성·테스트·배포를 완료했다는 기록은 아닙니다. 메뉴는 계정, 앱 버전, 조직 정책에 따라 다를 수 있습니다.

일반적인 테스트·배포 절차의 기준은 [운영 가이드](OPERATIONS.md)입니다. 이 문서는 클라우드 준비와 로컬 작업 인계만 보완합니다.

## 1. 권장 방식과 로컬 작업 비교

권장 흐름은 **GitHub에 작업 기준 준비 → Cloud에서 구현·자동 테스트 → PR 검토 → 로컬 화면 확인 → 병합·배포**입니다. 기존 로컬 프로젝트를 삭제하거나 웹사이트·Supabase를 이전할 필요는 없습니다.

| 항목 | 로컬 Codex | Codex Cloud |
|---|---|---|
| 실행 위치 | 현재 Windows PC | 클라우드의 별도 작업 공간 |
| PC 절전·종료 | 로컬 명령 실행 중단 | PC가 절전 상태여도 작업 지속 |
| 초기 준비 | 이미 설치한 도구 사용 | 저장소·런타임·테스트 도구 설정 |
| 파일 접근 | 로컬 변경사항과 허용된 자료에 접근 | 연결한 저장소와 별도로 제공한 자료 사용 |
| 화면 조정 | 브라우저를 보며 빠르게 반복 | 자동 검사 후 실제 기기 확인을 함께 수행 |
| 환경 차이 | Windows 권한·브라우저 환경의 영향 | 의존성·네트워크·서비스 설정의 영향 |
| 적합한 작업 | 디자인 미세 조정, 로컬 문제 재현 | 범위가 명확한 버그 수정, 리팩터링, 테스트 보강 |
| 사용량 | 구독 사용량 소비 | 로컬과 한도 공유, 작업에 따라 더 많이 소비 가능 |

Cloud는 작업별로 독립된 공간을 제공하며 웹·모바일·데스크톱에서 결과를 검토할 수 있습니다. [공식 개요](https://learn.chatgpt.com/docs/cloud)

Cloud를 별도의 무료 사용량으로 생각하면 안 됩니다. 모델·문맥·작업량에 따라 소모량이 달라지므로 현재 계정의 사용량 화면을 확인합니다. [공식 요금·사용량 안내](https://learn.chatgpt.com/docs/pricing)

## 2. 프로젝트에서 가져갈 것과 별도 준비할 것

작성 시 확인한 로컬 경로는 `D:\Workspace\travel\website`, 원격 저장소는 `https://github.com/pca01008/us-west-2027-trip.git`입니다. 당시 작업 브랜치는 `codex/modularize-travel-app`이며, 이후에는 실제 사용할 브랜치를 다시 확인해야 합니다.

| 대상 | 준비 방법 |
|---|---|
| 소스·생성 결과·문서·테스트 | 필요한 변경사항을 GitHub 작업 브랜치에 커밋·푸시 |
| 저장소의 `AGENTS.md` | 클라우드에서도 읽도록 작업에 명시 |
| 현재 대화의 결정사항 | 새 작업에 짧은 인계문 제공 |
| `.agents/`의 디자인 스킬 | Git 제외 대상이므로 필요한 스킬만 별도 준비 |
| 사용자 홈의 스킬·플러그인·인증 | 로컬과 동일하게 제공된다고 가정하지 말고 사용 가능 여부 확인 |
| `.secrets/`, `.env*` | Git에 추가하지 않고, 필요한 값만 환경 설정에서 제공 |
| 로컬 참고 이미지·여행 메모 | Git 제외 대상 여부 확인 후 필요한 자료만 제공 |
| 브라우저 로그인·IndexedDB 초안 | 자동 이전 대상이 아님. 필요한 초안은 기존 앱에서 저장·내보내기 |

GitHub 연결만으로 현재 PC의 폴더와 대화가 통째로 복제되지는 않습니다. 특히 일반 코드 검사에는 운영 DB 관리자 키나 실제 여행자의 로그인 정보가 필요하지 않습니다.

현재 웹사이트·데이터 구조와 소스 위치는 [프로젝트 가이드](PROJECT_GUIDE.md#source-modules)를 따릅니다. 현재 여행은 schema 6·KRW/USD를 유지합니다.

## 3. 로컬에서 작업 기준 준비

다음 명령은 저장소 폴더에서 실행합니다.

```powershell
git status --short --branch
git branch -vv
git log -1 --oneline --decorate
git remote -v
```

1. 사용할 브랜치와 현재 커밋을 확인합니다. 운영 코드에서 시작할지, 진행 중인 작업 브랜치에서 이어갈지 정합니다.
2. 미커밋 변경사항이 있다면 내용을 검토한 후 필요한 파일만 커밋합니다. 비밀 파일이나 개인 자료를 함께 추가하지 않습니다.
3. 작업 브랜치를 GitHub에 푸시하고 원격 상태를 확인합니다. 로컬에 기록된 `origin/...` 정보만으로 서버의 최신 상태까지 확인했다고 판단하지 않습니다.
4. 클라우드에 전달할 브랜치 이름과 기준 커밋 SHA를 기록합니다. 커밋 SHA는 `git rev-parse HEAD`로 확인합니다.

커밋·푸시 방법과 확인 항목은 [Git 및 배포](OPERATIONS.md#deployment), 권한 규칙은 [AGENTS.md](../AGENTS.md)를 따릅니다. Codex의 Windows 샌드박스에서 Git 메타데이터를 쓰는 명령은 승인된 권한으로 실행해야 합니다. 기존 `.git`을 삭제하거나 다시 만들지 않습니다.

로컬과 클라우드에서 같은 변경을 동시에 수정하면 합칠 때 충돌할 수 있습니다. 한 작업의 주 실행 위치를 정하고, 별도 작업은 별도 브랜치로 나누는 편이 간단합니다.

## 4. Codex Cloud 환경 생성

최신 공식 절차는 [Cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environments)를 기준으로 합니다.

1. ChatGPT 계정으로 웹 또는 데스크톱 앱에 로그인합니다.
2. 새 작업에서 `Work in → Cloud → Select environment → Create environment`를 선택합니다.
3. 또는 `Settings → Codex Cloud → Environments → Create environment`로 진입합니다.
4. GitHub 연결을 요청받으면 연결하고 `pca01008/us-west-2027-trip` 접근을 허용합니다.
5. 저장소를 선택하고 `Get started`로 준비를 시작합니다.
6. 아래 설정 요청문을 전달합니다. 브랜치 선택 UI가 있다면 사용할 브랜치를 선택하고, 실제 체크아웃 결과도 확인하도록 요청합니다.

처음에는 본인만 사용할 환경으로 만들고, 이름은 예를 들어 `us-west-2027-trip-dev`로 지정하면 구분하기 쉽습니다. Cloud 메뉴나 저장소가 보이지 않으면 먼저 10절을 확인합니다.

### 복사해서 사용할 환경 설정 요청문

```text
pca01008/us-west-2027-trip의 Codex Cloud 개발 환경을 준비해줘.

저장소의 AGENTS.md, docs/PROJECT_GUIDE.md, docs/OPERATIONS.md를 읽어줘.
Node.js 24와 잠금 파일을 사용해 npm ci를 실행하고,
npx playwright install --with-deps chromium으로 브라우저를 준비해줘.

npm run build, npm test, npm run test:browser를 실행해
환경이 준비되었는지 확인해줘. 빌드가 추적 파일을 바꾸면 차이를 보고해줘.
실패한 검사는 환경 문제와 코드 문제로 구분하고,
실행하지 못한 검사를 통과로 기록하지 마.

SQL 검사가 필요하면 별도의 폐기 가능한 PostgreSQL 17을 준비하고,
loopback 연결의 TRIP_SQL_TEST_URL로 npm run test:sql을 실행해줘.
운영 Supabase 또는 운영 DB를 테스트 대상으로 사용하지 마.

설치 과정은 Install script에, 매 작업에서 필요한 서비스 시작과
준비 확인은 Start skill에 반영해줘.
현재 로컬 전용 스킬이나 플러그인이 필요하면 사용 가능 여부를 확인해줘.
앱 배포나 운영 데이터 변경은 하지 말고, 환경 준비 결과를 보고해줘.
```

### 설치와 검증 명령의 구분

아래는 저장소 루트에서 실행하는 명령입니다. Node.js 24 설치는 환경 준비 과정에서 먼저 처리합니다.

```sh
# 설치: 최초 준비 또는 의존성 변경 시
npm ci
npx playwright install --with-deps chromium

# 검증: 환경 준비 완료 시, 이후 작업에서는 변경 범위에 맞춰 실행
npm run build
npm test
npm run test:browser
```

매 작업 시작 때 전체 검사를 무조건 반복할 필요는 없습니다. 실행 기준과 검사별 범위는 [검증 절차](OPERATIONS.md#validation)를 따릅니다.

현재 CI는 단위·SQL 검사에 Node 24, 브라우저 검사에 Node 22를 사용합니다. 따라서 Cloud를 Node 24로 통일해 확인한 결과가 모든 CI 조건과 완전히 같다고 표현하면 안 됩니다. 실제 설정은 [Validate 워크플로](../.github/workflows/validate.yml)를 확인합니다.

### SQL 검사 환경

Docker 사용 가능 여부는 클라우드 환경에서 확인해야 합니다. Docker가 없다는 이유로 운영 DB를 대신 연결하지 말고, 설치 가능한 PostgreSQL 서비스를 사용하거나 기존 CI의 SQL 검사를 활용합니다.

테스트 DB 준비 방식과 권한은 [운영 가이드의 SQL 검사](OPERATIONS.md#validation)를 따릅니다. 다음은 별도 테스트 서버가 `127.0.0.1:55439`에서 준비된 경우에만 사용하는 Bash 예시입니다.

```sh
export TRIP_SQL_TEST_URL='postgresql://postgres:trip-sql-local-only@127.0.0.1:55439/postgres'
npm run test:sql
unset TRIP_SQL_TEST_URL
```

위 비밀번호는 폐기 가능한 테스트 서버 예시입니다. 서버를 시작하거나 준비 상태를 확인하는 명령을 대신하지 않습니다. 테스트는 DB·역할을 생성·제거할 수 있으므로 다른 데이터를 가진 서버를 사용하지 않습니다.

## 5. 네트워크·비밀값·스킬 준비

### 네트워크와 비밀값

설치 중 필요한 npm 패키지 및 Playwright 다운로드 접근을 허용합니다. 막힌 경우 오류에 표시된 실제 다운로드 대상을 확인해 허용 범위를 조정합니다. 일반 모의 브라우저 검사를 위해 운영 Supabase 접속을 열 필요는 없습니다.

실제로 필요한 설정이 생기면 환경의 `Environment variables` 또는 `Network secrets`에서 제공할 수 있습니다. 전자는 프로그램이 직접 읽는 값, 후자는 지정한 HTTPS 대상에 전달할 자격 증명에 사용합니다. 구체적인 지원 범위와 적용 방식은 [공식 환경 설정 문서](https://learn.chatgpt.com/docs/environments/cloud-environments)를 확인합니다.

비밀값을 작업 프롬프트·문서·커밋에 붙여 넣지 않습니다. 로컬 `.secrets/` 전체를 옮기기보다 해당 작업에 필요한 값만 설정합니다.

### 디자인 스킬과 플러그인

이 저장소는 `.agents/`를 Git에서 제외합니다. 현재 사용 중인 디자인 스킬을 Cloud에서도 사용하려면 필요한 스킬 파일과 참조 자료를 별도로 준비하고, 클라우드에서 실제로 읽을 수 있는지 확인합니다. 사용 가능한 설치·연결 방식은 해당 환경에서 확인해야 합니다.

스킬을 저장소에 포함하기로 결정하더라도 `.agents/` 전체를 일괄 공개하지 말고 필요한 파일·라이선스·개인 자료 포함 여부를 먼저 검토합니다. 사용자 홈의 절대 경로나 Windows 전용 실행 명령이 있으면 환경에 맞게 조정합니다.

초기 Cloud 시험 작업은 디자인 스킬 없이도 가능한 작은 버그 수정이나 테스트 보강으로 선택하면 준비가 단순해집니다.

## 6. 준비 결과 검토와 환경 게시

다음 항목을 확인한 후 환경의 `Publish`를 선택합니다.

- 저장소와 런타임 버전이 맞는가?
- 의존성과 Chromium 설치가 완료되었는가?
- 실제 실행한 검사, 실패·미실행 검사가 구분되어 있는가?
- 불필요한 코드 변경이나 비밀 파일이 생기지 않았는가?
- 필요한 서비스가 새 작업에서도 시작되도록 준비되었는가?

`Environment published`가 나타나면 `Start a new task`로 시작합니다. **여기서 Publish는 재사용할 개발 환경을 확정하는 기능이며, GitHub Pages 배포가 아닙니다.** [공식 시작 절차](https://learn.chatgpt.com/docs/cloud)

## 7. 실제 작업 시작과 인계문

새 작업마다 저장소·기준 브랜치·범위·완료 조건을 전달합니다. 아래 대괄호 항목은 실제 값으로 교체합니다. 작성 당시 브랜치를 그대로 사용할 때만 `codex/modularize-travel-app`을 지정합니다.

```text
저장소: pca01008/us-west-2027-trip
기준 브랜치: [사용할 브랜치]
기준 커밋: [GitHub에 올린 커밋 SHA]
작업: [수정할 문제와 기대 동작]

시작 전에 기준 브랜치와 커밋이 맞는지 확인하고 작업 브랜치를 만들어줘.
현재 로컬 대화의 맥락은 다음과 같아: [결정사항과 제외 범위]

AGENTS.md와 관련 문서를 따라줘.
앱 수정은 src/에서 하고 npm run build로 생성 결과를 갱신해줘.
현재 여행의 schema 6·KRW/USD를 유지해줘.
Daylight 추가 개발과 운영 전환은 보류 상태야.
관련 문서를 구현 결과에 맞춰 갱신해줘.

변경 범위에 맞는 테스트를 실행하고, 성공·실패·미실행과 이유를 보고해줘.
완료하면 변경 요약과 검증 결과를 포함한 PR을 만들어줘.
main 병합, GitHub Pages 배포, 운영 DB 변경은 이번 작업 범위에 포함하지 마.
```

완료 조건은 “개선해줘”보다 “증상 재현 → 수정 → 해당 회귀 검사 → 관련 문서 갱신”처럼 구체적으로 적습니다. 현재 대화 전체가 자동으로 인계되었다고 가정하지 않습니다.

## 8. 결과 검토와 로컬 복귀

1. PR의 변경 파일과 기준 브랜치를 확인합니다. 의도하지 않은 여행 데이터·인증 설정 변경이 없는지 살펴봅니다.
2. `src/`와 생성 결과가 함께 변경되었는지 확인합니다. 최신 변경 이후의 검사 결과인지도 확인합니다.
3. GitHub Actions 결과를 확인합니다. Cloud에서 성공했다는 보고가 PR의 CI 성공을 대신하지는 않습니다.
4. 로컬의 미커밋 변경사항을 먼저 보존한 뒤 PR 작업 브랜치를 가져옵니다.
5. UI 변경이면 데스크톱·모바일 화면을 확인합니다. 모의 저장 검사와 실제 계정·기기의 검증 결과를 구분합니다.
6. 검토가 끝나면 [기존 배포 절차](OPERATIONS.md#deployment)에 따라 병합·배포합니다.

로컬 복귀는 Codex에 다음처럼 요청할 수 있습니다.

```text
[PR URL]의 작업을 현재 로컬 프로젝트에서 이어서 검토해줘.
먼저 로컬 변경사항과 원격 저장소를 확인하고 기존 작업을 보존해줘.
PR 브랜치를 가져와 변경 내용과 CI 결과를 확인한 다음,
필요한 로컬 검증과 화면 확인을 진행해줘.
아직 병합이나 운영 배포는 하지 마.
```

직접 Git 명령으로 처리한다면 일반 PowerShell에서 저장소 상태를 확인한 뒤 진행합니다. 브랜치 전환이 거부되면 강제 전환·초기화하지 말고 원인을 먼저 확인합니다. Codex가 실행할 때는 Windows Git 권한 규칙이 그대로 적용됩니다.

## 9. 환경을 나중에 수정할 때

의존성·도구·서비스 준비가 바뀌면 환경의 `Edit`에서 수정·검증하고 `Republish`합니다. 새 작업과 기존 작업은 같은 상태로 일괄 갱신되지 않으므로, 환경 변경을 확인할 때는 새 작업에서 재검증합니다. 중요한 결과는 Git에 커밋하거나 필요한 파일을 별도로 저장합니다. [저장 상태 및 환경 갱신](https://learn.chatgpt.com/docs/environments/cloud-environments)

`package-lock.json`이 변경되었다면 필요한 환경에서 `npm ci`가 다시 실행되었는지 확인합니다. 저장소 갱신만으로 새 의존성이나 서비스가 모두 준비되었다고 가정하지 않습니다.

## 10. 문제 해결

| 증상 | 확인할 사항과 대응 |
|---|---|
| Cloud 메뉴가 없음 | 계정 기능 제공 여부, 앱 버전, 조직 정책 확인. 웹에서도 확인 |
| 저장소가 목록에 없음 | 연결한 GitHub 계정과 해당 저장소 접근 권한 확인 |
| 원하는 변경사항이 없음 | 로컬 미커밋·미푸시 변경 여부, 기준 브랜치와 커밋 확인 |
| `npm ci` 실패 | Node 버전, 잠금 파일 일치 여부, 패키지 다운로드 접근 확인 |
| Chromium 실행 파일 없음 | `npx playwright install --with-deps chromium` 결과와 브라우저 캐시 경로 확인 |
| 브라우저 시스템 라이브러리 부족 | 설치 권한과 `--with-deps` 설치 결과 확인 |
| SQL 검사 실패·미실행 | 폐기 가능한 PostgreSQL의 실행 상태·권한·loopback URL 확인. 운영 DB로 우회하지 않음 |
| 스킬을 찾지 못함 | `.agents/` 제외 규칙과 클라우드의 실제 설치 상태 확인 |
| 테스트에 환경 변수가 없음 | 필요한 작업에 직접 전달되는 변수인지, 네트워크용 비밀값인지 구분 |
| Cloud는 통과했는데 CI 실패 | 커밋 SHA, Node 버전, 설치 명령, 환경 변수, 실패 로그 비교 |
| Windows의 ACL 오류를 Cloud에서 재현 못함 | Windows 고유 문제는 로컬에서 원래 로그·정확한 경로로 진단 |
| 작업 재개 후 내용이 다름 | 선택한 작업·브랜치·환경 확인. 기존 작업 상태와 새 환경 상태를 구분 |
| 변경했는데 운영 화면이 그대로임 | PR 생성·환경 Publish와 main 병합·Pages 배포를 구분. 배포 절차 확인 |

## 11. 첫 사용 완료 체크리스트

- [ ] 사용할 브랜치와 커밋을 GitHub에 준비했다.
- [ ] 필요한 로컬 결정사항과 자료를 인계했다.
- [ ] Node·의존성·Chromium을 준비하고 실제 검사 결과를 확인했다.
- [ ] SQL 검사를 실행했다면 독립된 테스트 DB를 사용했다.
- [ ] 작은 작업 한 건을 Cloud에서 수행하고 PR로 검토했다.
- [ ] 로컬에서 결과를 가져와 필요한 화면·기기 확인을 마쳤다.
- [ ] 병합·배포 여부와 미실행 검사를 별도로 기록했다.
