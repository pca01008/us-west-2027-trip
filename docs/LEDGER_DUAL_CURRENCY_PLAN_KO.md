# 가계부 원화·달러 동시 입력 수정 계획

작성일: 2026-10-24 (Asia/Seoul)
상태: **로컬 구현·단위/브라우저 검증 완료 / 실제 SQL 검증·서버 적용·배포 전**
구현 결과·검증·배포 조건: [구현 기록](archive/2026-10-24-ledger-dual-currency.md)
검토 기준: 로컬 `codex/legacy-ui-refinement`, 커밋 `f03e727`의 기존 앱. 공개 서버의 실제 지출 데이터는 조회하거나 변경하지 않았다.

## 1. 목적과 범위

여행 참가자 두 명이 지출마다 실제 원화 결제액과 달러 금액을 기록할 수 있게 한다. 기존 화면의 색상·카드·탐색 구조를 유지하고, 지출 입력과 계산에 필요한 부분만 바꾼다.

사용자가 요청한 동작:

- 지출을 추가할 때 원화(KRW)와 달러(USD)를 모두 입력할 수 있다.
- 하나만 입력하면 지정된 수동 환율로 다른 금액을 계산하고 자동 계산임을 표시한다.
- 둘 다 직접 입력하면 두 입력값을 그대로 사용하고 자동 계산 안내를 표시하지 않는다. 두 금액이 수동 환율과 일치할 필요는 없다.

추가·수정·목록·합계·CSV·초안·내보내기·복원까지 같은 규칙을 적용한다. 실시간 환율 API, 환율 이력 관리 화면, 건별 환율 입력 UI, 새 프레임워크는 추가하지 않는다. Daylight의 신규 기능 개발은 계속 보류하되 공유 데이터 손실을 막는 호환성 처리는 배포 조건에 포함한다.

현재 사용법은 [사용자 안내서](USER_GUIDE_KO.md#가계부), 저장 구조는 [기술 설명서](PROJECT_GUIDE_KO.md), 검증·배포는 [운영 안내서](OPERATIONS_KO.md#validation)가 기준이다. 아래 내용은 구현 전 설계 기록으로 보존하며, 최종 구현과 실행 결과는 상단의 구현 기록을 따른다.

## 2. 현재 구현에서 확인한 사항

| 영역 | 현재 구현 | 수정 이유 |
|---|---|---|
| 추가 | `index.html`의 `#expenseAmount`, `#expenseCurrency`, `addExpense()` | 금액 하나와 통화 하나만 받는다. |
| 수정 | `#expenseDialog`, `openExpenseDialog()`, `saveExpenseChanges()` | 수정 시에도 같은 단일 금액 구조를 사용한다. |
| 정규화 | `normalizeExpense()`, `normalizeExpenses()`, `normalizeState()` | `amount`, `currency`만 남겨서 새 필드를 추가하는 것만으로는 데이터가 보존되지 않는다. |
| 합계·목록 | `renderLedger()` | 통화별 원본 합계와 `KRW + USD × 현재 환율`을 계산한다. |
| 환율 | `updateExchangeRate()`, `#ledgerSettingsClose` 처리 | 공통 환율을 바꾸면 과거 지출의 환산 합계도 달라진다. |
| CSV | `exportExpensesCsv()` | 날짜·내용·카테고리·통화·금액·원화 환산액을 내보내고 현재 환율을 사용한다. |
| 입력 보존 | `applyStatePreservingInputs()` | 입력값·초점·선택 범위를 보존하지만 직접 입력/자동 계산 출처는 아직 없다. |
| 변경 비교 | `buildDiff()` | 금액·통화 변경만 비교하므로 새 금액과 출처도 비교해야 한다. |
| HTML 교체 | `sanitizeMarkup()`, `moneyTemplateHtml`, `IMPORT_ALLOWED_MONEY_IDS` | 과거 HTML의 가계부를 현재 템플릿으로 교체하고 허용 ID를 제한한다. |
| 저장 | `captureState()`, `applyState()`, `fingerprint()` 및 공유 저장·초안·버전 경로 | 정규화가 모든 저장·복구 경로에 영향을 준다. |
| 스키마 | `trip-config.js`, `trip-config.template.js`는 `schemaVersion: 5` | 두 통화의 확정값·출처를 구분하는 새 버전을 계획한다. |
| DB | `supabase_setup.sql`의 문서 `content jsonb`와 revision 검사 RPC | 지출 전용 테이블은 없다. 새 테이블 없이 문서 구조를 확장할 수 있다. |
| 병행 앱 | `daylight/index.html`, `daylight/trip-config.js` | 캐시 이름은 다르지만 같은 `tripId`를 사용하고 단일 금액 정규화 코드를 갖고 있다. |

현재 가계부 브라우저 검사에는 환율 변경 시 재계산, 합산 후 원화 반올림, 행별 CSV 반올림, 삭제된 카테고리, 표시 순서가 포함되어 있다. 새 규칙에 따라 기대값을 바꾸되 회귀 검사를 제거하지 않는다.

## 3. 입력·표시와 상태 전환

### 3.1 화면

- 기존 금액/통화 선택기를 `원화 (KRW)`와 `달러 (USD)` 두 입력란으로 바꾼다. 날짜·카테고리·항목·추가 버튼은 기존 흐름을 유지한다.
- 두 입력은 항상 편집 가능하게 한다. 자동 계산된 쪽도 직접 수정할 수 있다. 자동/수동 전환 스위치를 추가하지 않는다.
- 자동 계산한 입력 아래에만 `수동 환율로 자동 계산`을 표시한다. 목록과 수정 창에서도 계산된 금액 옆에 `자동 계산`을 표시한다.
- 자동 계산 안내는 저장된 출처로 판단한다. 금액이 환율 계산 결과와 우연히 같다는 이유로 표시하지 않는다.
- 두 금액을 직접 입력한 내역에는 자동 계산 안내와 환율 불일치 경고를 모두 표시하지 않는다.
- 목록에는 `₩14,500 · $10.00`처럼 두 금액을 같은 지출의 두 표현으로 보여 준다. `+`로 연결하지 않는다.
- PC에서는 두 금액을 나란히, 좁은 모바일에서는 세로로 배치한다. 고정 폭 때문에 큰 금액·오류 문구가 버튼과 겹치지 않게 한다.
- 각 입력에 실제 label을 연결하고 `inputmode="decimal"`을 사용한다. 오류는 해당 필드에 연결하고 제출 실패 시 첫 오류로 초점을 이동한다. 자동 안내는 색상만으로 구분하지 않으며 입력할 때마다 스크린리더가 과도하게 읽지 않게 한다.

### 3.2 내부 입력 상태

직접 입력한 문자열과 자동 계산 결과를 분리한다. 화면의 두 입력란에 숫자가 있다는 이유만으로 “둘 다 직접 입력”으로 바꾸지 않는다. 추가 폼과 수정 창은 각각 독립 상태를 가지며 작은 공통 계산 함수만 재사용한다.

| 사용자 조작/상태 | 동작 | 안내 |
|---|---|---|
| 둘 다 비어 있음 | 계산하지 않는다. 추가 시 최소 한 금액을 요구한다. | 없음 |
| 원화만 직접 입력 | 달러 = 원화 ÷ 수동 환율 | 달러에만 자동 계산 |
| 달러만 직접 입력 | 원화 = 달러 × 수동 환율 | 원화에만 자동 계산 |
| 자동 계산된 쪽에 직접 숫자를 입력 | 두 값 모두 직접 입력으로 전환하고 상대 금액을 보존한다. | 즉시 제거 |
| 둘 다 직접 입력한 상태에서 한쪽 수정 | 반대쪽은 바꾸지 않는다. | 없음 |
| 둘 다 직접 입력한 상태에서 한쪽을 비움 | 남은 직접 입력값으로 빈 쪽을 계산한다. | 계산된 쪽에 표시 |
| 한쪽만 직접 입력한 상태에서 원본을 비움 | 원본과 그에 의존하던 계산 결과를 모두 비운다. | 제거 |
| 자동 계산된 쪽만 비움 | 원본이 남아 있으므로 자동 상태를 유지하고 계산값을 다시 표시한다. | 유지 |
| 잘못된 문자열/입력 중인 소수점 | 원본 문자열은 유지한다. 계산 결과를 확정하지 않고 제출을 막는다. | 해당 필드 오류 |

자동 필드를 포커스하거나 선택만 해서는 출처가 바뀌지 않는다. 사용자가 실제 입력 이벤트로 같은 숫자를 다시 입력하면 직접 입력으로 인정한다. 붙여넣기·모바일 입력·한글 조합 중간 상태도 고려한다. 프로그램이 값을 채우는 처리를 사용자 입력으로 취급하지 않는다.

### 3.3 추가·수정·갱신

- `추가` 성공 시 항목명과 두 금액 및 출처를 함께 초기화한다. 인증 취소·검증 실패 시에는 그대로 둔다.
- 인증을 기다리는 동안 공유본이나 환율이 바뀔 수 있으므로, 실제 추가 직전에 최신 유효한 수동 환율과 입력 상태로 다시 검증한다. 두 직접 입력값은 재계산하지 않는다.
- 수정 창은 저장된 출처를 복원한다. 이름·날짜·카테고리만 수정하면 금액과 적용 환율을 바꾸지 않는다.
- 자동 출처가 있는 내역의 원본 금액을 수정하거나, 직접 입력값을 지워 자동 상태로 전환하면 현재 수동 환율로 다시 계산한다. 기존 기록을 단순히 여는 동작으로 재계산하지 않는다.
- 취소·Esc는 수정 창의 임시 상태를 버리고 기존 내역을 유지한다. 열려 있는 동안 해당 지출이 변경·삭제되면 오래된 값으로 덮어쓰지 않고 다시 확인하게 한다.
- 저장 응답·Realtime·재접속 후 입력 보존에는 두 직접 입력 문자열, 출처, 초점·커서도 포함한다. 최신 환율이 달라졌다면 미추가 폼의 자동 결과만 다시 계산한다.
- 기존과 같이 `추가` 전 입력은 IndexedDB 초안·공유 데이터에 넣지 않는다. 추가한 내역은 초안에 금액과 출처를 함께 보관하고 `변경사항 저장` 후 공유한다.

## 4. 금액·환율·합계 규칙 — 권장 설계

사용자 요청에는 과거 내역 재계산 정책이 명시되어 있지 않다. 건별 실제 결제액을 보존하려는 목적에 맞춰 **추가된 지출의 두 금액은 고정하고, 수동 환율 변경은 이후 자동 계산에만 적용**하는 안을 권장한다. 아래 정책은 구현 전 검토할 설계 가정이다.

1. 환율 단위는 `1 USD = R KRW`로 통일한다. 외부 시세를 가져오지 않는다.
2. 한쪽만 입력하면 계산된 금액과 그때 사용한 `R`을 지출에 저장한다. 현재 전역 환율로 목록을 다시 계산하지 않는다.
3. 두 금액을 직접 입력하면 각각 확정값으로 저장한다. 두 금액의 비율을 새 공통 환율로 설정하지 않는다.
4. 설정에는 짧게 `새 자동 계산에 적용`을 표시한다. 이미 추가된 내역을 일괄 재계산하는 기능은 만들지 않는다.
5. 원화 합계는 각 지출의 원화 금액 합, 달러 합계는 달러 금액 합이다. 둘은 같은 지출 목록을 다른 통화로 표현한 값이므로 서로 더하지 않는다.
6. 기존 세 합계 카드 중 중복되는 `원화 환산 합계`를 제거하고 `원화 합계`, `달러 합계` 두 카드로 정리한다. 카테고리 합계도 같은 규칙을 쓴다. 기존의 “실제 KRW 입력 항목만 합산한 값”과 의미가 달라짐을 문서에 명시한다.

### 금액 정밀도와 검증

- 새 직접 입력은 원화 정수, 달러 소수 둘째 자리까지 허용한다. 초과 소수 자릿수를 조용히 버리지 말고 `원 단위로 입력해 주세요`, `소수 둘째 자리까지 입력해 주세요`로 안내한다.
- 자동 계산은 원화는 1원, 달러는 1센트 단위로 양수 사사오입한다. 입력 중 표시와 저장 확정에 동일한 함수를 쓴다.
- `Number` 변환 전에 빈 문자열과 유효한 숫자 문자열을 구분한다. 공백·천 단위 쉼표를 정리하되 쉼표 위치가 잘못된 값, 지수 표기, 문자가 섞인 값은 거부한다.
- 직접 입력값은 유한한 양수여야 한다. 0·음수·Infinity·NaN은 거부한다. 자동 계산 결과가 매우 작아 0으로 반올림되는 경우는 원본 양수가 유효하면 허용하고 자동 안내를 유지한다. 이 0을 직접 입력값이나 빈칸으로 오인하지 않는다.
- 원화 정수와 달러 센트가 안전 정수 범위를 넘으면 거부한다. 수동 환율도 유한한 양수여야 하며 계산 중 범위 초과를 검증한다.
- 새 금액의 계산·합산은 최소 화폐 단위를 이용한다. 소수 환율은 문자열의 정수/소수 부분으로 처리해 이진 부동소수점의 경계 오차를 막는 작은 함수를 둔다. 큰 금액 라이브러리는 추가하지 않는다.
- 둘 다 직접 입력했다면 전역 환율의 유효성에 관계없이 두 금액을 저장할 수 있어야 한다. 자동 계산이 필요한 경우에만 유효한 환율을 요구한다.

## 5. 저장 구조와 기존 데이터

### 5.1 새 지출 구조

문서 스키마는 5에서 6으로 올리는 안이다. 지출마다 아래 필드를 둔다. 새 이름은 구현 시 일관되게 적용하되 동일 정보를 중복 관리하는 구조는 피한다.

```json
{
  "id": "expense-example",
  "name": "저녁",
  "date": "2027-01-21",
  "categoryId": "food",
  "amountKrw": 14500,
  "amountUsd": 10,
  "amountSource": "both",
  "appliedExchangeRate": null
}
```

| `amountSource` | 의미 | `appliedExchangeRate` |
|---|---|---|
| `krw` | 원화 직접 입력, 달러 자동 계산 | 계산에 사용한 환율 |
| `usd` | 달러 직접 입력, 원화 자동 계산 | 계산에 사용한 환율 |
| `both` | 두 금액 직접 입력 | `null` |

새 지출은 기존 `amount`·`currency`를 별도의 진실로 유지하지 않는다. 화면·비교·CSV가 모두 새 필드를 읽게 한다. 정규화는 유효한 새 필드를 보존하고 출처·환율의 조합을 검증한다. 손상된 새 데이터를 임의로 0이나 현재 환율로 덮어쓰지 않고 복구 가능한 오류로 처리한다.

### 5.2 스키마 5 이하 전환

- 구형 `amount`·`currency`에서 직접 입력 통화를 판별하고, **그 문서에 저장된 수동 환율**로 반대 통화 금액을 한 번 만든다. 현재 열려 있는 앱의 전역 환율을 섞지 않는다. 문서 환율이 유효하지 않으면 기존 기본 환율 대체 규칙을 따르고 이 사실을 전환 안내에 포함한다.
- 과거 거래 당시의 환율은 복원할 수 없다. 과거 내역에 적용하는 환율은 “전환 기준 환율”임을 명시한다. 최초 전환 시 `기존 내역은 저장된 환율로 계산해 유지합니다`라는 안내를 한 번 보여 준다.
- 원래 통화의 금액·ID·날짜·분류·순서는 보존한다. 현재 구현은 소수 원화 등도 저장할 수 있으므로 기존 소수 금액을 새 입력 규칙에 맞춰 몰래 잘라 내지 않는다. 기존 원본 정밀도를 허용하는 읽기/전환 경로와 새 입력 검증을 분리한다. 금액을 실제 수정할 때만 새 정밀도 규칙을 적용한다.
- 반대 통화의 새 계산값만 위 반올림 규칙을 적용한다. 행별 환산값을 고정하므로 구형의 “합산 후 환산·반올림” 결과와 소액 차이가 생길 수 있다. 전환 비교에 합계 차이를 보여 주고 과거 금액이 정확해졌다고 주장하지 않는다.
- 스키마 6의 유효한 금액은 재정규화·재열기·환율 변경 때 다시 변환하지 않는다. 같은 입력 문서의 전환 결과가 매번 동일해야 한다.
- 읽기만으로 서버에 자동 저장하지 않는다. 정규화된 저장 기준선과 초안을 같은 방식으로 만들어 가짜 미저장 표시를 막고, 사용자의 정상 저장 시 새 스키마를 반영한다.
- 구형 초안은 초안 상태와 기준 상태를 각각 그 상태의 환율로 변환한다. 버전 복원·오프라인 가져오기도 해당 문서 환율을 사용한다. 과거 버전 자체는 수정하지 않는다.
- 전환 전 작업본을 보관하고 최근 저장 버전으로 복구할 수 있게 한다. 롤백은 새 필드를 무시하는 구형 코드만 다시 배포하는 방식으로 하지 않는다.

### 5.3 구버전 클라이언트의 데이터 손실 방지

현재 정규화는 알지 못하는 지출 필드를 버리며, 스키마를 올리는 것만으로 기존에 열려 있는 탭의 저장을 막지는 못한다. 특히 Daylight에서 PREP 체크만 저장해도 문서 전체가 구형 구조로 정규화될 수 있다.

배포 조건:

1. 기존 앱과 Daylight에 미래 스키마를 감지하고 쓰기를 막는 최소 호환 처리를 먼저 준비한다. 안내는 `앱을 새로고침해 주세요`로 짧게 한다. Daylight에 새 입력 기능을 만드는 것은 범위 밖이다.
2. 서버의 기존 `save_trip_document` RPC에 현재 문서보다 낮은 스키마의 저장을 거부하는 작은 검사를 추가하는 안을 권장한다. 이미 열린 구형 탭·구형 오프라인 작업본까지 보호하려면 클라이언트만으로는 부족하다. 테이블·권한 체계를 새로 만들지 않는다.
3. `supabase_setup.sql`과 별도 증분 migration SQL을 같은 내용으로 맞춘다. revision 충돌 검사와 기존 편집자 권한 검사는 유지한다. SQL 적용은 실제 구현·배포 작업이며 이 계획 작성에서는 실행하지 않는다.
4. 공유 저장, PREP 즉시 저장, 버전 복원 등 모든 쓰기 경로가 이 RPC 보호를 받는지 확인한다. 새 클라이언트가 구형 버전을 복원할 때는 먼저 스키마 6으로 변환하므로 정상 복원이 가능해야 한다.
5. 지원 버전보다 새로운 데이터는 `normalizeState()`가 현재 버전으로 강제 변환하기 전에 거부한다. 읽지 못하는 데이터를 빈 화면·빈 배열로 대체해 저장하지 않는다.

## 6. CSV·비교·내보내기

- CSV 열은 `날짜, 내용, 카테고리, 원화 금액, 달러 금액, 자동 계산 통화, 적용 환율`로 정리한다. 자동 출처가 없으면 마지막 두 열은 비운다.
- 내보내는 금액은 저장된 두 금액이다. 현재 환율로 새로 계산하지 않는다. 기존 소수 원화는 CSV에서 원본 정밀도를 보존하며 화면 원화 표시와의 반올림 차이는 안내서에 남긴다.
- UTF-8 BOM, CRLF, 따옴표·쉼표·줄바꿈 처리와 수식 접두 문자 방어를 유지한다. 빈 목록은 열 제목만 내보낸다.
- 버전/가져오기 비교는 양쪽 금액, 출처, 적용 환율 변경을 각각 비교한다. 같은 숫자를 자동에서 직접 입력으로 바꾼 경우도 실제 변경으로 감지한다.
- 오프라인 작업본·인쇄/공유 사본·JSON 상태·IndexedDB 초안에서 두 금액과 자동 안내가 일치해야 한다. 안내는 렌더링 시 상태로부터 만들고 중복 저장하지 않는다.

## 8. 검증 시나리오와 완료 기준

기본 고정 환율은 `1 USD = 1,400 KRW`로 사용한다. 기대값을 앱 계산 함수를 호출해 만들지 않는다.

| 시나리오 | 기대 결과 |
|---|---|
| 원화 14,000만 입력 | 달러 10.00, 달러만 자동 안내 |
| 달러 10.00만 입력 | 원화 14,000, 원화만 자동 안내 |
| 원화 14,500·달러 10.00 직접 입력 | 두 값 보존, 자동 안내 없음 |
| 자동 계산값 10.00을 직접 다시 입력 | 숫자는 같아도 출처는 `both`, 안내 제거 |
| 두 직접 입력 중 하나를 지움 | 남은 값 기준 자동 상태로 전환 |
| 자동 상태에서 원본 삭제·다시 입력 | 결과도 비워졌다가 다시 계산, 자동 결과가 원본으로 승격되지 않음 |
| 원화 1 입력 | 달러 0.00 자동 계산을 허용, 빈칸과 구분 |
| 환율 1,350에서 달러 0.01 입력 | 원화 14, 반올림 경계 검증 |
| 저장된 달러 10/원화 14,000 이후 환율을 1,500으로 변경 | 기존 지출은 14,000 유지, 새 달러 10 지출은 15,000 |
| 이름·카테고리만 수정 | 금액·출처·적용 환율 유지 |
| 두 지출: 14,000/10 자동 + 14,500/10 직접 | 원화 합계 28,500, 달러 합계 20.00, 이중 합산 없음 |
| 잘못된 수·소수 자릿수·0·음수·빈칸·범위 초과 | 해당 입력에 오류, 저장하지 않고 입력 보존 |
| 인증 지연·취소·성공 | 입력 유실 없음, 성공 직전 검증, 중복 추가 없음 |
| 저장 응답·원격 갱신·재접속 중 미추가 입력 | 직접 값·출처·초점·커서 보존, 자동 부분만 최신 환율 적용 |
| 실행 취소/재실행·새로고침 초안 복구 | 금액뿐 아니라 출처·자동 안내 복원 |
| 구형 문서·초안·과거 버전·작업본 | 각 문서 환율로 동일하게 전환, 기존 원본값·ID·순서 보존, 반복 전환 없음 |
| 기존 소수 원화·행별 반올림 차이 | 원본 정밀도 보존, 예상 합계 차이와 CSV 값 검증 |
| 새 스키마 문서를 구형/Daylight가 저장 | 서버에서 하향 저장 거부, 공유 데이터 유지 |
| 새 앱에서 과거 버전 복원 | 변환 후 새 스키마로 정상 저장 |
| 손상된 새 필드·지원하지 않는 미래 버전 | 덮어쓰기 없이 오류, 기존 초안 보존 |
| CSV·오프라인 작업본·인쇄본 | 두 금액과 자동 출처 일치, CSV 보안·한글 보존 |
| 카테고리 삭제·순서 변경·빈 목록 | 기존 동작 유지, 금액/출처 유실 없음 |

실제 구현 후 실행할 검사:

```sh
npm test
node scripts/check-ledger-browser.mjs
node scripts/check-drafts-browser.mjs
node scripts/check-imports-browser.mjs
node scripts/check-inputs-browser.mjs
npm run test:sql
```

공통 상태·저장 경로까지 변경하므로 위 검사 후 `npm run test:browser`로 통합 회귀를 확인한다. PC와 모바일 실제 렌더링에서 두 입력·긴 금액·안내·오류·키보드 이동·수정 창을 확인한다. 배포 전에는 서버 보호 migration을 먼저 적용하고, 새 앱과 남아 있는 구형 탭의 저장 동작을 검증한다. 모의 서버 결과와 운영 서버 확인은 구분해 기록한다.

완료 기준은 요청한 세 입력 방식의 동작, 건별 금액 보존, 합계의 이중 계산 방지, 모든 저장/복구 경로의 출처 보존, 구버전 덮어쓰기 방지, 관련 문서 갱신 및 위 검증 통과다.
